# 0248 librados compatibility adapter
Status: accepted
Date: 2026-10-15
Context: user explicitly requests continued implementation through functional qualification and librados drop-in replacement, extending earlier W/N-only scope. Native runtime remains independent, single-owner and efficient while idle. Original C ABI permits foreign calling threads and callbacks; full original CephContext/C++ interoperability is unresolved.
Decision: activate C/F compatibility work in own Rust crates/rados-ffi, default-off librados-compat feature, independent C exports over native runtime. Initial Linux x86_64 pinned v20.2.4 / v21.2.0 artifacts are the qualification anchor (21.1.2 replaced by 21.2.0, 2026-10-30); native ARM and exact consumer/distribution matrix remain gates. Per-family own specs/tests, original artifact manifests and unchanged independently written consumer binaries under private loader path. No original-library forwarding or global installation. Implement lifetime/completion substrate before asynchronous I/O. Keep Rust core free of C handles/callbacks/locks; adapter owns synchronization and future submission handoff. Preserve original completed-vs-callback-finished distinction and callback self-release. Native owner never crosses threads; worker must construct/own it locally.
Consequences: extra copies/synchronization at legacy boundary may be necessary. Full C and C++ claims require complete actual symbol/version/layout/semantic and foreign-context/consumer evidence; partial progress is not unrestricted replacement. C++ feasibility/foreign-context audit required alongside C implementation, not silently excluded. No Ceph code/header copy or linkage in replacement. RDMA/RBD remain separate implementations.
Alternatives: native-only delivery no longer satisfies latest user request; reference forwarding violates independence; share/move !Send native owner behind unsafe Send rejected; blanket unsupported exports do not establish parity.
