# 0595 Preserve request semantics and backfill progress after refusal

Status: accepted
Date: 2026-10-26

## Context

Execution rewrites a tail ZERO to TRUNCATE against projected state. Reexecution can follow failure of an earlier EC write, restoring a larger object. WRITESAME carries a small pattern but produces a larger store write. A failed backfill continuation must not leave a batch waiting for a push that no longer exists.

## Decision

- Reexecution restores original request opcodes and unions; reply echoes retain the completed execution's representation.
- WRITESAME admission charges its expanded byte length; aggregate cost arithmetic saturates instead of wrapping.
- Replicated backfill continuation errors cancel the batch without advancing its cursor, release reservations and use the existing stalled-backfill transition.

## Rationale

The original operation must be reevaluated against the state of each execution. Store admission must cover generated bytes before logging. Batch cancellation preserves the target's incomplete status while allowing repair and the existing reservation retry to proceed.

## Consequences

- + Interrupted ZERO requests preserve bytes outside the requested range.
- + Insufficient space rejects compact writes before logging instead of failing the OSD during apply.
- + Failed backfill chunks neither advance incomplete data nor leave writes blocked indefinitely.
- + Shared executor fixes cover replicated/EC pools, kernel/SPDK storage, knet/AF_XDP/RDMA and CRC/secure framing; DPDK uses the same code.
- + EC backfill already cancels failed rebuilds through `ec_recov_fail`; ordinary replicated recovery restarts pushes from its missing set.
- + No on-disk or wire-format changes.
- - Saved retry state adds one opcode per operation, keeping the four-op inline capacity.

## Alternatives

- Keep the rewritten opcode: a retry can truncate bytes outside the original ZERO range.
- Drop only the failed object's backfill marker: incorrectly permits batch completion with an incomplete target.
