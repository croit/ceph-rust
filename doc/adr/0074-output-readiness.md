# 0074 Per-core output readiness
Status: accepted
Date: 2026-10-13
Context: finding 5; both production transports enumerated every connection and allocated an ID vector on output flush.
Decision: messenger output registers with a per-core deduplicated queue, reserving capacity at connection creation. Monitor and relayed output notify their corresponding socket/core queue. Transports consume notifications; blocked output is retried on socket writability or send/connect completion. Handoff detaches its source registration before crossing cores. Existing `conn_ids` API remains for lab drivers/introspection.
Consequences: idle output flushing is constant work without ID-vector allocation. One cold registration allocation per connection; no locks/atomics in the queue. Per-core event pumping/timer scans remain separate costs. Tests/numbers: `perf/codex-perf-2026-10-13.md`. No wire/disk changes.
Amendment 1 (2026-10-13, lost wake-up): `Connection::send_message` queued into the session without notifying; frames are built only in `pump` (from `poll_output*`). Replies queued outside `on_bytes` (store completion, cross-core relay) waited until unrelated input on that link marked it (an ACK), i.e. the client's next op or keepalive: ~15 s stalls, 430-690 MB/s on icelake-6330-host1 4M writes. Fix: `send_message` notifies when Ready. Safety net: `Osd::sweep_output` every 10 ms (`OUTPUT_SWEEP`) re-arms any link/monc/pipe with pending output (bytes, queued messages, owed ACK) and no queued notification; finds are counted (`output_missed`) and logged once per tick (`output sweep: N lost output wake-ups`), must stay 0. Tests: `msgr2 session::reply_queued_outside_on_bytes_wakes_transport_and_sweep_finds_lost_marks`, `osd core_tests::output_ready_ignores_idle_connections_and_deduplicates`. Live icelake-6330-host1 osd.8 (interleaved vs main with 2062868d reverted, 3 rounds): 4M w 1p 2486 vs 2469 MB/s, max lat 0.08 s; 8p 2955 vs 2928 MB/s; no stall, sweep finds 0.
Amendment 2 (2026-10-15, own-TCP window shrink deadlock; root cause of the DPDK "laggy after restart" stall): live icelake-6330 (rep4m r1-A/r2-B, ec4m r3-B, ~1 of 4 runs) one core of each of two OSDs counted `output sweep` finds at exactly 100/s for the whole rest of the run (one link re-armed per 10 ms sweep, socket send queue full, never drained), osd.6 core 0 <-> osd.8 core 2 = both ends of one peer TCP connection; lease acks behind it -> PGs laggy, ops blocked; no fault, osd.8 core 2 `rto=9`. Cause (crates/net, not the sweep/msgr2/rt output path): `Tcb::adv_window` floored the scaled window field, so the advertised right edge retreated by up to 2^wscale-1 (127) bytes. A sender that had already filled the old edge then holds flight > snd_wnd; its ACK-only segments carry seq = snd_una + snd_wnd (Linux `tcp_acceptable_seq` rule) below the peer's rcv_nxt and the peer drops them (RFC 793 acceptability, ACK field ignored). One side in that state heals with the peer's next ACK; with both directions saturated and both readers slow (4M repops both ways after a restart) both ends can enter it at once: no ACK is ever accepted again, every retransmission is entirely old data (dropped too), RTO backs off to 60 s until `max_retries` kills the connection. Fix: round the scaled window UP (never shrink, RFC 7323 2.4 / Linux); `rcv_adv` starts at the SYN / SYN-ACK advertised edge (the first scaled ACK could fall below it with a small `rcv_wnd_max`). The sweep "finds" are mostly plain socket backpressure > 10 ms (rep4m runs without a stall: 40-120 per OSD); only a find rate of 100/s per core means a stuck link. Test: `net sim_features::window_right_edge_never_retreats_and_bidirectional_slow_readers_never_stall` (both directions saturated, slow random reads, rcv_wnd_max 20-60 KB, shift 7): before, seed 3 stalls for good after 0.7 s (A flight 5792 > snd_wnd 5760, B same) and every run shows right-edge retreats; after, none. No wire format change (window values only; at most 127 bytes more advertised than buffer room, `rcv_limit` already honours `rcv_adv`).

Amendment 3 (2026-10-16, resolves OQ 43: blocked is not lost): the sweep counted links whose socket was merely backpressured (send queue full, `flush_one` got WouldBlock; send in flight on knet) as lost wake-ups: pending output + no notification looks identical to a lost mark from the OSD core (socket state lives in the transport); ~100/s under rep3 4M, misread as a wake-up bug (gitlab issue #2). Fix: `Link.out_blocked` flag, set by the transport via `Osd::set_output_blocked(conn, bool)` (`Driver` trait default no-op; `OsdNet` = DPDK/own TCP: true on `poll_writable` WouldBlock, false when the queue drained / socket dead; `KNet` = kernel tier: true when `flush_one` finds a send in flight, false at its completion, which pulls the rest). Transports track the last told value per conn and call only on change (no lookup on the steady path, no alloc, no lock). `sweep_output` skips blocked links (never re-arms them: Writable / send completion flushes) and counts them in `output_blocked_skips` (expected). `output_missed` and the "lost output wake-ups (bug)" log now mean what they say: any find there is a real bug, since a link is only skipped while the transport has said it will flush it. Pipes (cross-core relay) and monc unchanged. Only a stuck blocked link (never Writable) stays invisible to the sweep: that is a transport/TCP fault (see am. 2), seen as stalls, not here. Test: `osd core_tests::sweep_skips_backpressured_link_but_still_finds_lost_wakeup`; existing `output_ready_ignores_idle_connections_and_deduplicates` keeps the lost case.

Amendment 4 (2026-10-17, invariant instead of sweep; supersedes the sweep of am. 1 and the blocked flag of am. 3): invariant: a producer that queues output notifies the core's output queue (`notify` from `send_message` / `pump` / `process` / pipe / monc), and the core runs `flush_out` on EVERY loop iteration, so no notification survives into a park; a notification consumed while the transport cannot pull (send in flight, dial in flight) is owed by the transport itself (knet `on_send` pulls when its queue drains, `on_connect` flushes; DPDK `Event::Writable` / `Connected`). Root cause of the kernel-tier ms tails: `KCore::step` (and `core_loop`) ran `flush_out` only when an input source reported "driven"; producers outside those return values (e.g. `settle_late` inside `poll_store` making a deferred txn durable at once -> reply / repop queued, `poll_store` false) left the notification queued while the core parked, until unrelated input or the 10 ms `OUTPUT_SWEEP` timer fired. The 1-2/s sweep "finds" under replica load were not lost wake-ups: knet output still held in `c.out` beyond one `sendmsg` (MAX_IOV / `send_chunk`) after the completion had cleared `blocked`, monc / pipe ids during a send (never marked blocked), cut-through tx progress between `WAKE_STEP` wakes; all owned by the transport or the stream wake. Fix: `KNet::output_pass` / `core_loop`: `pump_io` when driven (unchanged), `flush_out` always (empty queue = one `RefCell` pop); `flush_out` returns whether a connection was ready (counts as work, refreshes `next_timer`). Removed: `OUTPUT_SWEEP`, `Osd::sweep_output`, `output_missed` log line, `Driver::set_output_blocked`, `Link.out_blocked`, knet/OsdNet `blocked`, `Connection::rearm_output`, `MonClient::rearm_output`, `OutputNotify::is_pending`; cut-through uses `Connection::wake_output` (notify if `has_output`). Audit (no recovery): `Osd::note_park` right before the knet core parks counts a park with a non-empty output queue: perf dump `osd.knet_wake_parked_ready`, must stay 0. Tests: `rt knet::tests::undriven_iteration_still_flushes_queued_output` (fails with the old driven-gated flush), `consumed_notification_stays_owed_across_partial_sends`, `osd core_tests::park_with_queued_output_is_counted_as_lost_wakeup`, `msgr2 session::reply_queued_outside_on_bytes_wakes_transport`, `pending_ack_piggybacks_after_application_dispatch_and_one_way_still_wakes`. Lab gate: `lab/baremetal/knet-wake-gate.sh [--format json] fix/knet-wakeup main` (r3 replica load w4kq16 + w4m8, 2 alternating rounds, LAB=zen4; pass = counter 0 on every gate OSD after every cell and mean p99.9 new <= main + 10 %, no WARNING TIMEOUT; handoff doc/perf/knet-wake-20261017.md). Siblings: the same driven-gated flush in rt::core_loop (DPDK) is fixed in the same commit; no live DPDK/AF_XDP cell runnable in the labs (see the handoff doc).
