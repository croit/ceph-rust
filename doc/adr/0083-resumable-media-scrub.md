# 0083 Resumable deep-scrub data and asynchronous media reads

Status: accepted, amended (am. 4)
Date: 2026-10-13
Context: performance finding 1. A deep-scrub slice budget previously applied between objects only; a large object's complete data digest blocked its owning core. Media reads used synchronous batches of 16 commands. The adapter also used the ordinary read API, which could consume client prefetch or decompressed-cache contents.

Decision:
- Retain offset, running data digest, object size/visible attrs, EC mode, and omap digest in the existing one-slot-per-PG scrub continuation. Restart on object/version or EC-mode change, using the existing size/attrs validity rule. Invalidate the old physical read continuation on restart.
- Bound a data read to the smaller of the 4 MiB stride and the slice byte budget, with a one-block minimum. Yield on IO/durability/capacity waits and between data strides once the budget is spent. EC digests use the same continuation and existing finish rules.
- Extend ADR 0078 rolling reads to explicit media verification. Media continuations are keyed separately and bypass both client prefetch and the decompressed cache. Completions refill device queue slots without batch barriers. Existing four-session, 32 MiB DMA, queue-reserve, reader-pin and expiration bounds apply. A completed slice releases its retained results; in-flight cancelled commands remain charged until completion.
- Use a private scrub session namespace and restore caller nonblocking/media/session state after every attempt. Preserve visibility/durability fences and ADR 0082 FIFO/ack behavior. No disk, WAL or wire format change.
- Primary and replica chunk startup explicitly discard any abandoned continuation, even when object attrs/size are unchanged, so a fresh scrub verifies its prefix again.

Consequences: large-object deep scrub yields the core and verifies fresh device bytes. One data stride may overshoot a tiny byte budget by at most its block minimum; omap retains its existing batch granularity. Scrub competes within the bounded rolling-read capacity. A cancelled scrub is reclaimed by the existing continuation TTL. Metadata enumeration/stat/attrs and omap access retain their existing synchronous behavior.

Alternatives: a separate scrub IO scheduler duplicates queue/pin machinery; synchronous stride-sized slices still block for device latency; trusting client caches would hide media corruption.

Validation: large-object continuation and zero virtual device wait, object-version invalidation, corruption underneath client prefetch, EC digest parity, affected store/storeadapt suites and store release model/crash soaks. Measurements and limitations: `../perf/codex-perf3-2026-10-13.md`.

## Amendment 1: 1 MiB deep-scrub slices, configurable (2026-10-15; crates peering/osd(config))
Measured (icelake-6330 VMs, `lab/baremetal/tail.sh`, rep3 64 PG, 8 GiB image, `osd pool deep-scrub` at +20 s under rbd 4K randwrite, NV_PHASE stall lines): with 8 MiB slices the longest core iteration (osd timer / io pump) was 64-120 ms (every scrubbing PG of a core digests its slice in the same iteration; an operator pool scrub starts all PGs); client write max 3.0-5.0 s, 8x QD16 p99.99 217-238 ms.
Decision: `SLICE_BYTES` 8 -> 1 MiB default, `ScrubCfg::slice_bytes` from `flashstore_scrub_slice_bytes` (>= one block); `osd_scrub_sleep` now feeds `ScrubCfg::sleep` (was parsed nowhere).
Result (same block, 1 MiB vs 8 MiB, one run each): longest iteration 14 vs 64-112 ms; QD1 write IOPS 2944 vs 2449, max 1.0 vs 3.0 s; 8x QD16 37.2k vs 34.2k IOPS, p99.99 144 vs 217 ms, max 2.4 vs 4.5 s. Remaining second-scale max = writes waiting for the scrubbed chunk (by design) and all PGs scrubbing at once (operator request bypasses `osd_max_scrubs`; open, tail-latency-20261015.md).
Tests: peering `scrub_primary.rs` `deep_scrub_with_tiny_slices_finds_the_corruption`.

## Amendment 2: scrub concurrency and chunk preemption (2026-10-15; crates peering/osd(config); lab tail.sh, docker mixed case 19)
Problem (icelake-6330 VMs, tail-latency-20261015.md): `osd pool deep-scrub` started every PG of the pool at once (operator requests bypassed `osd_max_scrubs` and replica reservations; the configured `osd_max_scrubs` never reached the slots, hard-wired 3); the scrub start of all PGs stalled cores 16 ms per iteration and writes waited for the chunk of their PG: rep3 8x QD16 write max 2.4 s, p99.99 291 ms, QD1 max 1.7 s.
Classic (v21 scrubber): operator urgency skips reservations and the concurrency limit, but the OSD tick starts at most one scrub per second; replicas count reservations separately from own scrubs; `osd_scrub_max_preemptions` (5) lets a client write preempt the chunk (it is retried with a halved size), after that writes wait.
Decision:
- `osd_max_scrubs` wired (start + runtime) to the local (primary) slot pool and the replica reservation pool, OSD-wide value split over the cores (rounded up, >= 1 per core, like `osd_max_backfills`).
- `flashstore_scrub_operator_limits` (default true): operator and follow-up scrubs queue FIFO for a local slot and reserve every replica (sequential REQUEST wait=true, the periodic path; classic replicas grant it like a periodic request). False = classic: no reservation, no limit (`force`). Periodic scrubs unchanged (refused slot = retry later). An operator REPAIR (`ceph pg repair`, MOSDScrub2 repair=1; not the auto-repair follow-up) is never limited: classic force path, no slot wait, no replica reservation (a reservation wait could stall it). Deadlock-free: replica slots are a separate pool, reserved in ascending OSD order.
- Preemption (`osd_scrub_max_preemptions`, 0 = writes always wait): a write into the active chunk passes; the chunk is dropped at once if its requests are not out, else marked preempted (writes pass, own build stops, the maps already asked for are drained and dropped, never compared) and re-selected from the same start with chunk min/max divided by 2^preemptions (floor 3 objects or the configured minimum). `allow_preemption` stays false on the wire: replicas see only ordinary requests.
Result (icelake-6330 VMs, tail.sh, main 0364664 vs this, one run each, deep scrub of rep3 tailr 64 PG at +20 s): 8x QD16 write IOPS 29.0k / 32.3k, p99.9 22.2 / 29.5 ms, p99.99 292 / 46 ms, max 2400 / 79 ms; 1x QD1 IOPS 2658 / 2612, p99.99 6.6 / 8.7 ms, max 1747 / 52 ms. All 64 PGs deep-scrubbed inside the 150 s cell.
Interop: docker mixed case 19 (`lab/docker/mixed/19-scrub-resv.sh`, classic v21.1.2 + 3 croit-flashstore-osd, own iso lab): pool deep-scrub of mx-mix under rbd IO, `osd_max_scrubs` 1: complete in 113 s, croit-flashstore-osd local/replica slot peaks 1/1, classic replicas held reservations for 6 croit-flashstore-primary PGs, 0 errors, md5 clean, classic healthy. Wire unchanged (MOSDScrubReserve as for periodic scrubs): same on 20.2.x classic OSDs.
Tests: peering `scrub_primary.rs` `writes_preempt_the_chunk_until_the_budget_is_spent`, `operator_scrubs_observe_max_scrubs`, `operator_scrubs_classic_bypass_the_limit`, `operator_repair_bypasses_the_limit`; `writes_to_the_active_chunk_are_blocked` runs with 0 preemptions.

## Amendment 3: replica reservations in (osd, shard) order, no reservation timeout, failed targets stay pending (2026-10-20; crate peering; OQ 28 O19)
Problem: knet (8 cores, `osd_max_scrubs` 3 = 1 replica slot per core) optimized-EC gate, round 4 of two runs: operator deep scrubs of 9.0 / 9.8 ended "scrub: reservation timed out" twice, late GRANTs arrived after the aborts ("scrub reserve reply without session"), then nothing (the aborted session had consumed the operator request). am. 2's "ascending OSD order" held only for replicated pools: EC sessions reserved by shard position, so PGs whose acting sets are rotations ([0,1,2], [1,2,0], [2,0,1]) each held one replica slot and waited for the next: a cycle only the 120 s timeout broke. Classic: reservations in ascending `pg_shard_t` (osd, shard) of the sorted acting set, no reservation timeout (v21 `scrub_reservations.h` still describes one, the code has none), a failed target keeps its urgency (`delay_on_failure` moves only its not-before).
Decision: REQUESTs go out in ascending (osd, shard) for every pool type; the reservation wait has no timeout (`ScrubCfg::reserve_timeout` removed; an interval change ends the session, replicas always answer); an unfinished session (abort, interval change, local reject) puts its operator request / repair verification back, retried after `retry` (30 s); `scrub-abort` drops it. Replica slots stay per core (OSD value split over the cores, am. 2): ordering by OSD keeps the per-core pools cycle-free; OSD-wide accounting is open (90-open-questions.md 28 O19).
Diagnostics: `dump_pgs` per PG `scrub` (session phase, member asked with nonce and age, members left / granted, pending request, aborts, replica reservation), `repops_held`, `core`; per core `parked` (waiting for map / PG / old-map replay); `dropped` summed (was always 0).
Siblings: replicated pools already sorted by OSD (not affected); transport (knet / AF_XDP / DPDK) and store tiers not involved (scheduling only); single-core builds had the same cycle (1 pool per OSD), rarer with 3 slots.
Tests: peering `ec_primary.rs` `operator_scrubs_of_rotated_ec_pgs_never_wait_on_each_other` (stalls before), `scrub_primary.rs` `operator_request_survives_an_aborted_session` (fails before); lab ecbad default-gate fails on an unfinished deep scrub (scrubcap.sh capture).

## Amendment 4: OSD-wide scrub budgets, replacing am. 2's per-core split (2026-10-31; crates peering/osd; spec/scrub.md 11)
Problem: am. 2 split `osd_max_scrubs` over the PG cores, rounded up, >= 1 per core: 8 cores and `osd_max_scrubs` 1 ran up to 8 concurrent local scrubs and 8 replica reservations, 8x the load the operator configured (mixed case 19: "local scrubs 2 > 1"). Classic bounds the whole OSD.
Decision: two OSD-wide budgets of `osd_max_scrubs` each, local scrubs and replica reservations counted separately like classic, not split. Core 0 (the only core when single) keeps them (`ScrubSlots`, FIFO per pool). The other cores send `XMsg::ScrubSlot` (request: immediate or queued, force, release) and receive `XMsg::ScrubSlotReply` on the same ordered lane. Each core numbers its requests; a reply whose number is no longer the open one (released or replaced meanwhile) is ignored, so a late grant never counts as a later request's slot. The owner remembers requesting core and number per PG: a release from a core the PG has left (placement move) does not free the new holder's slot. A slot granted to a PG that is gone is released at once; releases on interval change, reset, removal and merge are the PG's existing release actions (a release of a slot never asked for is dropped). `dump_scrub_reservations` lists the owner's slots, the control core sums the cores: OSD-wide counts.
Rationale: a scrub start or end is rare (seconds apart at best), so one cross-core round trip costs nothing and no lock, atomic or shared structure touches a hot path; thread-per-core ownership stays (adr 0006, 0031). Classic order, FIFO and idempotent release unchanged.
Consequences: the 1-per-core minimum is gone: `osd_max_scrubs` 1 = one scrub per OSD. A replica GRANT / REJECT and a local grant take one core round trip more. Shutdown frees everything with the process; an interval change frees via the PG's release.
Siblings: `osd_max_backfills` and snap-trim slots had the same split: generalized into the same mechanism in adr 0031 am. 9; knet / AF_XDP / SPDK / kernel NVMe, replicated / EC, crc / secure not involved (scheduling only).
Tests: peering `scrub::slot_tests` (budget 1 over 8 cores never above 1, FIFO pass-on, immediate reject, former-core release), `pgset::scrub_slot_tests` (vanished PG gives its slot back, stale reply ignored), existing `scrub_primary.rs` / `ec_primary.rs` release-on-interval-change asserts; lab: mixed case 19, unchanged strict check.
