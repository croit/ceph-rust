# 0025 OSD on the NVMe store (M2.5): persistence, async commit, failure policy
Status: accepted, amended (am. 1)
Date: 2026-10-09
Context: M2 hosted PGs on `DevMemStore` (RAM, lost on restart). The storage engine (0021) and adapter exist; the OSD must run on them, survive restart/kill -9 by peering via log (no backfill), and never panic on remote input.
Decision:
- **One store per device, identity inside it.** `mkfs` formats the device (`--dev file:PATH[,size=N]` DEV/LAB ONLY | `spdk:PCI`), then provisions identity/key/superblock as objects of the engine's meta collection (`identity`, `superblock`, `osdmap.<e>`, `inc.<e>`, `m.<key>`; `osd::nvmestore::NvmeMeta` implements `MetaStore`). No keyring/identity files; `FileMetaStore` (+ `DevMemStore`) stays only as the legacy `--data DIR` dev mode. The pending uuid/secret of an interrupted mkfs lives in the store (`m.mkfs-pending`), so a crash after `osd new` re-uses them.
- **Device selection** by `nvme::any::{DevSpec, AnyCtrl, AnyDev}` (one concrete type). `FileDev` (`pread/pwrite`, completes writes only after one `fdatasync` covering them, reports `vwc=false`) exists only so the OSD runs without NVMe (docker lab, macOS); production = `SpdkDev`. Lab geometry: files < 256 GiB get 4 shards x 64 MiB WAL.
- **Mount at start** (WAL replay). PGs found in the store are loaded in `Osd::start` (`PgSet::load_pgs`): the retained osdmaps `[min PG epoch .. current]` are rebuilt from stored full/incremental blobs first (interval checks), PG messages produced before boot are dropped (nobody should hear from us until booted; the new up_from starts a new interval anyway). Map blobs are trimmed below `min(mon trim bound, min PG epoch)` keeping the newest full map at or before it. Holes in the stored history (epochs never received: mon trim = classic skip_maps) are crossed at the next stored full map. A PG starts at the map of its persisted epoch, else the first retained map after it (`PgSet::start_map`); it is removed for a missing pool only by a map AT or AFTER its epoch (pool ids are never reused: only that proves the deletion). A PG whose start map would be older and lacks its pool is NOT loaded, kept on disk, ERROR log + cluster log (am. 2026-10-11, oq 14: a chain cut at a hole made 28 of 32 PGs of a new pool look deleted and removed them). Map persistence never creates holes itself: MonClient queues each `OsdMap` event with the map AT its epoch before anything that sends (a send drains the session and handled the next buffered MOSDMap re-entrantly: events came out newest first, the OSD stored the newer map, skipped the older event as old and never stored its epochs); a full map past a gap the mon still has is not taken (osd-lifecycle 3.5 step 4).
- **Async commit.** `Action::Persist` -> `PgStoreOps::queue(spg, txn, token)` (staged and visible at once) -> `Queued::{Durable, Pending, Rejected, Failed}`; the driver calls `Osd::poll_store` every loop iteration (like the NIC): `PgStoreOps::poll_commits` -> `PgSet::on_commit`. The adapter maps (pg, token) <-> engine token. Ack discipline unchanged: nothing is acknowledged before durable. Still blocking inside the loop: engine misses (tree page / data reads, Busy waits) spin the shard (blocking driver, 0021 impl note 9); meta writes (map commit) wait for durability; `RemovePg` runs its chunks synchronously.
- **Remote input never panics.** Malformed transaction (decode error, bad collection, range > 128 MiB, clone of missing source, unsupported op) = `Rejected`: nothing applied, not acked, logged + counted, the sending link is closed; undecodable PG messages are dropped, link closed after 8; PG message from a non-OSD peer closes the link. `MemStore` follows the same rules (validates before applying; Truncate/rename/remove of missing = no-op, Clone/CloneRange2 of missing source = error, source offset past the end reads zeros).
- **Local store failure** (EIO, ENOSPC, engine error, dead device on commit/poll/load) = sticky `PgStoreOps::failed()`: the OSD stops serving (`pg.dead`), sends MOSDMarkMeDown through the normal shutdown path and exits with code 1. Durable state stays consistent (engine rule: failed checkpoint/commit leaves the last root valid). No panic, no retry.
Consequences: + restart/kill -9 comes back with its PGs and peers via log; + core loop polls the store without per-txn blocking for PG writes (group commit by the shard); - rejected txn leaves its PG un-acked until the interval changes (primary hangs on us); - FileDev throughput = fdatasync rate; - `spdk:` inside the DPDK-net daemon needs SPDK's env to share the EAL (not wired; the tool initializes SPDK itself).
Alternatives: keep a directory for identity (two durability domains, rejected); ack-and-skip bad txns (lies about durability); panic on commit failure (kills the process mid-write without telling the mon).

Amendment 1 (one PG pass per store poll, 2026-10-24, implemented; doc/perf/store-completion-20261024.md): `Osd::poll_store` hands every txn one `poll_commits` reaped (group commit makes several durable together) to `PgSet::on_commit` in completion order, collects their actions in that order and runs them in ONE `pg_exec` (one engine sync, one retry pass over the parked ops, one reply flush) instead of one `pg_exec` per txn. Ack discipline unchanged (a reply still needs the txn durable; the engine sees the write completions in the same order); the only difference: commit k+1 reaches the PG machinery before the actions of commit k run (sends, store queues, engine write completions: they keep their order among themselves). Counters `commit_polls` / `commits` (`dump_pgs` counters, per core) give the txns per pass. Rationale: the per-pass costs (engine sync, parked-op scan, clock reads, action queue) were paid per txn.
