# 0165 NVMe interrupt-driven completion for the kernel tier: evaluated, not implemented
Status: evaluated, deferred (lab VMs cannot run it; budget math says marginal). No code change.
Date: 2026-10-17
Context: adr 0162 am. 1: CPU/op during a store wait = spin wall time; the only lever left is sleeping through the 70-90 us device wait with a precise wake. Candidate: SPDK NVMe PCIe interrupt mode (`spdk_nvme_ctrlr_opts.enable_interrupts`, `spdk_nvme_qpair_get_fd()`), eventfd polled by the core's io_uring.
Findings:
- API present in the SPDK we build (v26.09, `/opt/spdk` on build host): `enable_interrupts`, `spdk_nvme_qpair_get_fd`, `nvme_pcie_qpair_get_fd`, `spdk_pci_device_enable_interrupts(dev, efd_count)`. Primary process only (no secondary processes). One MSI-X vector + eventfd per IO qpair needs `interrupt_cap_multi` = VFIO MSI-X ("Enable PCI device interrupts, only if VFIO MSI-X is supported", env.h). uio_pci_generic offers one legacy INTx line, no per-qpair vectors: not usable.
- Lab VMs (Zen 4 test VM <test-vm-ip> checked directly; icelake-6330 Ice Lake VMs per vm-prep.sh/conf.sh, not re-checked: bench lock not obtained): no guest IOMMU (`/sys/kernel/iommu_groups` empty), Debian 6.12 kernel without CONFIG_VFIO_NOIOMMU (no `enable_unsafe_noiommu_mode`), so vfio-pci cannot bind; that is why vm-prep.sh falls back to uio_pci_generic (IOVA=PA). Options: vIOMMU in the VM definition (hypervisor change: forbidden for agents) or an out-of-tree vfio.ko rebuilt with NOIOMMU inside the VM (kernel source + headers per VM, taints, nothing production-like). MSI-X itself is visible in the VMs (PM1743 Count=128), so passthrough delivery is not the blocker, VFIO is.
- Production bare metal: IOMMU on + vfio-pci is already the documented requirement (adr 0004), so the mechanism would work there with no deploy change (intel_iommu=on / amd_iommu, `vfio-pci` bind, hugepages as today).
- Wake latency, measured (`lab/baremetal/wake-lat.rs`: waker thread signals an eventfd after D us busy wait, waiter blocked in read(), different vCPUs, Zen 4 VM, 1500 iters/cell): signal -> return from read() p50 7.6-7.8 us, p90 8.2-8.9, p99 12-15 us for D = 20..90 us (spin baseline 0.1 us). That is cross-vCPU IPI wake only; a real MSI-X adds device -> host -> guest interrupt injection (posted interrupt to a halted vCPU needs a host wake) and the io_uring completion, unmeasured (needs VFIO).
- Budget: accept criterion is p50 not above the BlueStore baseline on the same hardware (equal within noise or better); the former +3 % = 8 us tolerance is dropped. The sleep/wake path alone costs ~8 us, before MSI-X delivery. Expected outcome on the VMs: CPU/op -35..-45 % (the 70-90 us spin disappears, only wake + processing remain), p50 +3..+6 %. Fails or barely meets the criterion; q16 unaffected (never idle). Hybrid (poll a short window, then sleep) does not fix it: the sleep decision is made before the completion time is known; an early timer wake (adr 0162 sweep, 50 %) already showed +10-20 % p50 for the same reason.
Decision: do not implement now. Revisit on production bare metal (IOMMU, no virtualization: interrupt -> wake is typically a few us with C1 only) where the measurement is possible, with: `enable_interrupts` per qpair, eventfd read armed in kcore's ring as a multishot poll, hybrid = adr 0162 timer park to ~25 % then interrupt sleep, runtime switch default off until measured, uio path unchanged.
Next steps if picked up: (1) `wake-lat` + a raw VFIO MSI-X probe on a bare-metal node to get the real completion-to-wake number; (2) if p50 overhead < 4 us, implement the knet side (qpair fd -> ring poll, re-arm on wake, `NV_KNET_IRQ`), DPDK tier untouched.
Consequences: CPU/op stays at the adr 0162 level (~168 us s1-r4k1 on Ice Lake VMs). No new risk. The probe stays in-tree as a reproducible measurement.
