# 0041 Scope v1.1: CephFS on replicated pools (metadata + data), no cls
Status: accepted
Date: 2026-10-10
Context: adr/0013 lists "RGW/CephFS cls" as out. Spec doc/spec/cephfs-osd-surface.md (own words): MDS, ceph-fuse, kernel client and libcephfs use plain RADOS ops only (no `call`, no watch/notify, no pgnls on the normal path). cls_cephfs = disaster-recovery tool (cephfs-data-scan) + PGNLS filter; cls_journal = rbd journaling. Gap/plan: doc/spec/cephfs-gap.md.
Decision:
1. In scope (v1.1): CephFS with replicated metadata pool and replicated data pool(s), size 1-3, all-croit-flashstore-osd or mixed with classic OSDs. Snapshots incl. trimming (adr/0037) are in. Quotas = MDS/client side (no OSD work); RADOS pool quotas as before.
2. Out stays out: cls_cephfs (accumulate_inode_metadata, PGLS filter `cephfs.inode_tag`), cls_journal, `copy-from2` (kernel falls back on per-op EOPNOTSUPP; unknown op in a compound must answer per-op EOPNOTSUPP), EC data pool (adr/0010, later), pool snaps, cephfs-mirror/NFS (watch/notify exists; untested). Tools needing them (cephfs-data-scan) are unsupported on croit-flashstore-osd pools until a later ADR.
3. No new code path for the runtime: work = CephFS-shaped tests (caps from `ceph fs authorize` strings, cmpxattr U64 uninline, stat/read at snapid, flag/unknown-op tolerance, clones in recovery/backfill/scrub), omap/journal workload benches (dirfrag-shaped omap, unaligned journal appends), live lab (lab/docker/cephfs).
4. Prime safety rule unchanged: unsupported ops/classes never crash or confuse classic OSDs/mons.
Consequences: + MDS journaling/dirfrags on croit-flashstore-osd without cls. - data-scan/recovery tools need classic OSDs or a later cls_cephfs (S method + S-M filter plumbing). - adr/0013 "Out: RGW/CephFS cls" is refined, not contradicted: CephFS runtime needs no cls.

## Amendment 1 (2026-10-10): store changes found by the CephFS-shaped tests/benches (services/osd/store)
Findings (sim + PM1743 `croit-flashstore-tool bench --fs`): (a) deleting an object (or `omap-rm-key-range`/`omap-clear`) whose omap exceeded `max_walk_pages` (2048 pages = 16 MiB of tree; ~20k dirfrag keys of 2.7 KB) returned `ObjError::TooLarge`; for the primary's own txn the OSD treats that as a failed local store and EXITS (`store_failed`) = a client could kill the OSD with one `delete`. (b) A 10 MiB dirfrag batch touching > cache/4 distinct pages (8192-page cache => 16 MiB) got the same fate. (c) Cold `omap-get-vals` page (1024 keys, 0.5-5 KB values): one serial blocking device read per leaf and per fragment leaf = ~12 ms (10k-key frag) / ~25 ms (100k keys) core stall per request.
Changes:
1. `Tree::del_range`: leaves lying completely inside the range are freed by address without being read (only interior pages + the two boundary leaves are loaded; `probe_range_ex(.., skip)`; `prefetch_range` keeps loading everything). 100k-key dirfrag delete = one txn, 1.6-2.5 ms, no leaf read. Crash tests: `big_omap_delete_crash_matrix` (every device event x 3 policies, fsck) + model/tree/crash suites unchanged.
2. `txn_page_budget` = cache/2 (was /4; eviction protection window follows) and `cache_pages` default 16384 (128 MiB/shard; was 8192). A txn whose distinct tree pages exceed the budget is still `TooLarge` (see open items).
3. Cold scans: `Tree::scan` queues the next <= 32 sibling leaves of the parent on a miss (parallel reads), `scan_vals` prefetches the fragment range of the page's keys (`Tree::prefetch_some`, <= cache/4 pages). Cold 1024-key page 12 ms -> 1.9 ms (10k keys), 25 ms -> 2.1 ms (100k keys).
Open (not done): own-txn `TooLarge`/`Rejected` is still fatal for the OSD (needs a pre-validated txn or a restartable submit); scan blocking is shorter, not gone (park the PG op like `warm`); unaligned-append RMW read per append (store reads the previous partial block, ~30 us blocking in the core loop; hot-tail-block cache keyed by (pba, crc) would remove it); per-shard meta region (meta_pct) holds all omap + fragments: 4 x 100k-key dirfrags (1.1 GB) filled one 1.7 GB shard meta region (backlog/oq 4d).

## Amendment 2 (2026-10-10): oversized client txn = EMSGSIZE, never an OSD exit
`PgStoreOps::check_write` (called by `Pg::submit_write` after the degraded/scrub gates, BEFORE log append and repop) lets the store refuse a txn it can never apply: `WriteErr::TooBig(errno)` -> engine replies a plain `-EMSGSIZE` (client-ops 5.4 rule 14b), no log entry, nothing cached, PG unaffected. storeadapt: wire size >= 64 KiB -> translate (borrowing) -> `Store::txn_needs_check` (op-weight/byte estimate vs page budget, ring, 8 MiB data) -> exact dry run `Store::check_txn` (stage + `Shard::check_fits`: record vs ring/2, distinct pages vs budget/2 (margin for replica tree shape), data extents vs queue depth; cold pages loaded blocking like `queue`; reservations released). Malformed/untranslatable txns -> EINVAL, ENOSPC -> ENOSPC. Replicas never see such a txn; a replica-side Rejected still closes the link (unchanged). Tests: store `check_txn_matches_queue_on_page_budget`, storeadapt `checkwrite.rs`, opexec `cephfs.rs::oversized_txn_is_refused_without_log_entry`. Closes the open item of amendment 1 (own-txn TooLarge fatal) for client writes; PG-internal txns (log claims, trims) keep the ADR 0028 guarantees.
