# 0093 Shared preparation budget and retained materialization
Status: accepted
Date: 2026-10-14
Context: performance findings 5 and 6. The Wave 2 branch gate is clear. Per-shard between-transaction budgets allowed four large compressed preparations to occupy one Store::poll for milliseconds. Allocation backpressure discarded finished compression. ADR 0082 and amendment 1 remain the ordering and durability contract.

Decision:
- Poll mandatory IO completions first. Then give all queued shards one 100 us / 128-step preparation allowance, with a rotating starting shard. Each visited FIFO head and each physical materialization quantum consumes a step. Keep the existing eight-attempt per-shard cap. A first visit and first data quantum may proceed after the time deadline to guarantee progress; this is a cooperative allowance, not a hard wall-time bound.
- Defer writes with more than 256 KiB of input data to that queue. Small synchronous warm submissions and permanent metadata-size validation retain their existing path. Successful queued adapter translation happens once; acquire immutable Bytes owners for borrowed input and retain the translated transaction. Shared input is never mutated.
- After dependency discovery, retain the private Stage overlay, dirty runs, object/run/block cursor, DMA prefix and reservations. Resume materialization at one compression chunk or at most one 64-block raw physical run per step. Partial allocator results advance by the actual number of blocks. Preserve original adjacent-run compression eligibility and compression feature state across slices.
- Retain a completed compressed encoding and logical CRC across allocation WouldBlock. Retain a rejected compression decision until its raw fallback completes. Do not re-copy, CRC or compress a completed prefix. A newly required compression feature retains the existing durable feature barrier and restaging rule.
- Only the shard FIFO head owns saved preparation. CPU yields explicitly schedule another poll; IO stalls still wait for the existing progress signal. Later writes remain fenced. Publish only a fully prepared transaction through the existing submit path; acknowledge only through durable completion. Rejection, timeout and device failure release every saved physical reservation exactly once.
- The retained prefix is part of the existing separately bounded prepared-head storage; input remains charged to its shard admission limits. First ownership conversion may allocate metadata nodes and borrowed-only payload storage. Existing wire owners are shared without a full-payload copy. Later slices move retained state rather than rebuilding it.

Limits: metadata apply/discovery/finalization, structural/feature barriers and exact primary size preflight remain synchronous. The allowance bounds repeated queued data/compression work, not every possible Store operation or mandatory completion processing. One codec quantum can exceed 100 us; there is no hard real-time guarantee. Offline commit/preflight paths remain unsliced, preserving their error and feature semantics. No wire, on-disk, placement or Ceph submodule changes.

Validation: four-shard 4 MiB compressed writes; rotating progress and one translation per input; allocation-stalled encoding reuse; timeout reservation cleanup; same-object FIFO/read fence; rejection at the queue cap preserves its partial head; crash during partial preparation under three persistence policies; retained-owner pointer/content checks. Full affected crates, store crash matrices and release model/crash/compression soaks. Measurements and reproduction: ../perf/codex-perf3-2026-10-13.md.

Amendment 1 (2026-10-14, deterministic sim schedule): the 100 us deadline read the host wall clock even under `SimClock`, so host load changed how many heads/quanta a poll prepared and thus the IO event sequence (parked crash matrix flaked: reference run 30 events, cut runs 28 -> "uncovered IO event 28"). `Clock::wall_time()` (SimClock: false) disables the deadline under virtual time; step bounds still apply. `Store::set_prep_allowance` overrides it; tests use `Some(ZERO)` for the most fragmented schedule (one head/quantum per poll). The parked crash matrix runs every IO cut x 3 policies for both schedules and asserts a repeat run issues the same event count. Production behavior unchanged.
