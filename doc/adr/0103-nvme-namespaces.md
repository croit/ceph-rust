# 0103 NVMe namespaces: one OSD per controller

Status: accepted (2026-10-14)

Context: a colleague split one NVMe into several namespaces and ran an OSD per namespace (`spdk:<pci>,ns=N`). Findings (code review + lab VM, PM1743 `MZWLO1T9HCJR` 03:00.0, re-laid out as ns1 960 GB 4096+0 / ns2 120 GB 512+0, restored afterwards):
- Format NVM scope. mkfs `--format-lba4k` sent Format NVM for the target NSID without looking at Identify Controller FNA. FNA bit 0 = a format of one namespace formats every namespace of the subsystem (bit 1 = same for secure erase). Preparing ns=2 could wipe ns=1 (another OSD). The lab drive reports FNA 0x04 (crypto erase only; per-namespace format): ns2 formatted 512 -> 4096 in 5.2 s, ns1 store intact; the risk is real on drives with FNA bit 0 set.
- One process per controller. SPDK attaches the whole PCI function (all namespaces, admin queue, BARs); the cross-process PCI claim (`/run/croit-flashstore-osd/spdk_pci_lock_<bdf>`, crate `nvme::pcilock`; adr 0649 am. 1) is per BDF. A second OSD on another namespace of a claimed controller cannot start. The daemons (`prod.rs`, `kprod.rs`) took the claim only after the EAL / SPDK env had already probed and mapped the device (tools did it before); the refusal came late, with exit 1 (systemd restart loop) and named only a pid. On uio hosts a mapping second opener can stop the owner's DMA (see `pcilock`).
- Rest is per namespace already: geometry (LBA size/count, max transfer, NAWUPF override), LBA format query/format target, `DevSpec ns=`. Controller-wide by nature: identity (model/serial = `ceph device ls` id; all namespaces share it, same as classic), SMART (global log), lock file, VWC/PLP. systemd units are per OSD id. `run` compared conf `flashstore_dev` against the prepared dir by PCI only (ns ignored).

Decision (v1):
- One croit-flashstore-osd OSD per NVMe controller (PCI function). Supported: a single namespace, or several namespaces of which exactly one is used by croit-flashstore-osd while nothing else on the host uses the controller (SPDK takes it away from the kernel). Several OSDs per drive are not needed for performance: one croit-flashstore-osd scales with cores (adr 0031), unlike classic `osds_per_device=2`.
- Format NVM only when it provably touches the target namespace alone (`nvme::fna::check_format_scope`): FNA bits 0/1 clear, or the subsystem holds one namespace (allocated list, Identify CNS 10h, when namespace management exists; else the attached set for a single-controller subsystem; unknown = refuse). Otherwise refuse with the remedy: create the namespace with a 4096+0 LBA format (`nvme create-ns --flbas`) and skip `--format-lba4k`, or evacuate all namespaces and format with nvme-cli. `inspect` shows `namespaces {fna, active, allocated, format_nvm_scope}`.
- The daemons take the PCI claim before the EAL / SPDK env init, exit 3 when held (no restart loop, `RestartPreventExitStatus=2 3`). The error names the holder (`osd.N (croit-flashstore-osd, pid P)` from `/proc/<pid>/cmdline`, else `process P (comm)`) and states the one-OSD-per-controller rule.
- `prepare` refuses a device on a controller that already holds another prepared OSD (other namespace), naming it. `run` compares conf vs dir by PCI and namespace. `ns=0` and `ns=0xffffffff` (broadcast) are rejected at parse time.

Options for real multi-namespace support (not implemented):
1. One OSD per controller (chosen, KISS). Cost: operators re-lay out drives to one namespace (or use one). No new code paths.
2. One croit-flashstore-osd process serving several namespaces as several OSDs (shared controller + EAL, per-OSD cores/qpairs, per-OSD msgr/mon sessions, health per OSD). Correct ownership model for SPDK, but a multi-OSD process changes the daemon model (systemd per id, crash domain = all OSDs of the drive, asok/metrics/logging per OSD, config sections). Large; little benefit since one OSD already uses the whole drive.
3. SPDK multi-process (primary/secondary, shared hugepages + `shm_id`). Secondary processes share the controller; the primary must outlive them; a crash of the primary stops every OSD on the drive; fragile across versions; adds a lock-free shared-memory dependency between OSDs. Rejected.
4. Kernel NVMe per namespace (io_uring passthrough `/dev/ngXnY`, or block `/dev/nvmeXnY`). Each namespace is an ordinary device; any number of processes, mixes with classic OSDs on other namespaces. Costs the SPDK path (adr 0004): kernel per-IO overhead, no polled userspace queues. Natural fit for the kernel tier (adr 0053) later: `file:`/kernel device class exists only as lab today; a production kernel-NVMe backend would be its own ADR.

Drop-in vs classic deployments with namespaces: classic `ceph-volume lvm batch` / cephadm drive groups put one OSD on each `/dev/nvmeXnY` (or `osds_per_device` LVs). Each namespace is a kernel block device, so classic OSDs coexist on one controller. For croit-flashstore-osd (SPDK): migrate a drive by draining all its classic OSDs, deleting the namespaces, creating one namespace (4096+0), then `croit-flashstore-tool prepare --dev spdk:<pci>`. A drive cannot be split between classic OSDs and croit-flashstore-osd. `ceph device ls` identity is model_serial for both (namespaces share it). Option 4 would be required to replace classic OSDs namespace by namespace in place.

Consequences: no multi-OSD drives in v1; misconfigurations fail early and clearly instead of wiping or hanging another OSD. Open: option 4 when the kernel tier gets a production NVMe backend (90-open-questions).

Validation: unit tests `nvme::fna` (decision matrix), `nvme::pcilock::holder_names_the_osd`, `nvme::any::parse_specs` (ns validation), `osddir` (`same_dev`, `controller_neighbours`, run conf vs dir by ns). Lab VM (prod build): second daemon on `ns=2` while `spdk_nvme_perf` drives `ns=1`: before = refused after EAL probe, exit 1, pid only; after = refused before EAL, exit 3, `process <pid> (spdk_nvme_perf)`; the perf run was unaffected in both cases. `inspect ns=2`: `fna 4, active 2, allocated 2, scope namespace`.

Amendment (am. 1, adr 0463): option 3 (SPDK multi-process) is available behind cargo feature `spdk-mp` for debug/testing builds only; production stays one OSD per controller.
