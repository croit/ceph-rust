# 0060 Small object classes: registered set, own HMAC-SHA1 for otp, `lua` not supported
Status: accepted
Date: 2026-10-11
Context: adr/0044 left cmpomap, sem_set, 2pc_queue, otp, numops (and cas, cephfs, hello, sdk, lua) unregistered. They are small, self-contained over `ClsCtx`, and needed for RGW multisite sync (cmpomap, sem_set), persistent notifications (2pc_queue), MFA (otp), plus cephfs-data-scan and the upstream gtests.
Decision:
- Registered (spec per class `spec/cls_<name>.md`, impl `services/osd/cls/src/<name>.rs`, `2pc_queue` = `tpc_queue.rs`): `hello`, `sdk`, `numops`, `cmpomap`, `sem_set`, `cas`, `2pc_queue`, `otp`, `cephfs`. Same rules as adr/0044 (byte-exact persisted data, classic flags, bug-compat marked).
- `otp` crypto: **own SHA-1/HMAC-SHA1 (~50 lines, `otp.rs`), no crypto crate.** Only TOTP/HOTP with SHA-1 exists in the class (liboath `oath_totp_validate2`); a dependency (hmac+sha1, digest, crypto-common, generic-array...) would add supply-chain surface to the OSD for one primitive used at admin rates. Own code is pinned by RFC 3174/2202/4226/6238 vectors in `tests/otp.rs`. Not a general crypto facility: anything needing SHA-2 or constant-time compare later uses a vetted crate (adr/0018), not this module. TOTP compare is not constant-time (same as liboath strcmp; the 5-attempts-per-step rate limit is the protection).
- `otp` safety deviations from classic: `step_size == 0` fails the check (classic divides by zero in the OSD), `window` clamped to 1000 (classic loops 2w+1 HMACs unbounded). Base32 seeds accept a superset of the classic decoder.
- **`lua` is NOT supported.** The class embeds a Lua interpreter that executes client-supplied scripts inside the OSD op thread (`eval_json`/`eval_bufferlist`), with access to the cls surface. Rejected: (1) arbitrary code in the thread-per-core hot path (adr/0006: no unbounded work, no allocation), (2) interpreter + bindings are a large C dependency and attack surface in a PLP/perf-critical daemon, (3) not in upstream `osd_class_default_list` (neither is `sdk`), so classic clusters need an explicit opt-in too; no known production user (RGW/RBD/CephFS never call it). Behaviour: class stays unregistered -> classification fails for the message (cls.md s2.1), counted under `cls_unsupported{lua}` (`unsupported::TRACKED` already has it). Revisit only on a concrete customer need; if ever, as a sandboxed fuel-limited interpreter behind a cargo feature, never in the default build.
- `sdk` (upstream test class for the SDK header) and `hello` are trivial and registered as [CW]: they are the executor's probes for flag enforcement (-EIO), RETURNVEC and -EOVERFLOW.
- `cephfs`: upstream has exactly one method, `accumulate_inode_metadata` (there is no `inject_inode`; cephfs-data-scan injects with ordinary ops). The PGLS filter `inode_tag` and `hello`'s filter belong to the pg-ls executor, not the registry (not implemented).
- `cas`: registered with `references_chunk` permanently `-ENOLINK` (no manifest objects/tiering, adr/0013): new `ClsCtx::manifest_ref_count` defaulted to 0.
Consequences: + RGW multisite sync status, datalog trim guards, persistent topic queues, MFA and `cephfs-data-scan scan_extents` no longer degrade on croit-flashstore-osd pools; + gtests for these classes can run; - `numops add/mul` on a missing key treats it as 0 (current-main code returns -ENOENT, but classic 21.1.1 passes the upstream gtest that expects success; we follow the passing behaviour); - own crypto code to maintain (frozen, vector-tested).
Alternatives: `hmac`+`sha1` crates (rejected above); aws-lc (already in the dependency graph for TLS, but a heavy, C-based dependency for the cls crate); registering `lua` returning -EOPNOTSUPP per method (rejected: unregistered gives the same client-visible result, one place fewer to maintain).
