# 0162 Kernel tier: park an idle core during a store IO wait
Status: accepted (default 10 % since am. 2, kill switch `--knet-store-park 0` / `NV_KNET_STORE_PARK=0`)
Date: 2026-10-17
Context: stage profile 2026-10-16 (adr 0161 context): nv 4k read CPU 190 us/op vs BlueStore 147, "store_commit" 148 us/op. Re-analysis of the raw on-CPU profile (s1-r4k1): only ~1 % of core samples are in `nvme_pcie_qpair_*`/`spdk_nvme_qpair_process_completions` (qpair is polled only with IO in flight, spdk.rs `poll`). The "store_commit" bucket is the whole event loop spinning (`poll_store`, `knet` poll, `XPort::pump`, `clock_gettime`) for the 70-90 us device wait: with IO in flight the idle policy polls up to `STORE_SPIN` (100 us) since the last work (adr 0085). Qpair polling is not the cost; loop iterations are.
Decision: `kcore::IdleState` tracks store busy spans (`store_quiet()` flips, checked on work and idle iterations; one clock read per span start). Short-span latency is learned per core (asymmetric EWMA: down 1/4, up 1/16, cap 2 ms, ~p20). After a span starts, an idle core sleeps in the ring (`wait_if`, woken by network/mesh pokes) until `start + pct % of the estimate` (pct default 25, spans < 15 us not parked), then polls as before (STORE_SPIN, ring waits). Spans are anchored at the first submit of a busy period, so pipelined load (store never quiet) behaves as before. 0 = previous policy exactly. Counters on the `knet:` exit line: `store_wait` (idle iterations with IO in flight), `park`, `park_ms`, `over_ms` (sleep beyond the requested cap), `io_est_us`.

Measurements: doc/perf/adr-0162-history.md (A/B and sweep tables)
Sweep (s1, 1 run each, `park-sweep.sh`): 50 % saves a little more CPU (145) but r4k1 p50 +10-20 % (timer wake overshoots the completion); 25 % keeps latency flat. Not done: r3 w4k1 (not rerun), per-device-class estimate (reads vs writes share one estimate), real interrupt-driven completion (SPDK userspace: not available).
Consequences: r4k1 CPU -14 %, still above BlueStore (147); remaining cost = the spin after the park (75 % of the wait) and the loop iteration weight (`poll_store` ~1 us/iteration: candidate for a slimmer idle-poll path). Wake overshoot is bounded by the 25 % margin.

## Am. 1 (2026-10-17): slimmer wait loop tried, rejected
Premise checked: while a core waits for a store completion it spins, so CPU/op = wall time of the wait; a cheaper loop iteration does not lower CPU/op (only parking does). Tried (branch `perf/knet-loop`, not merged): (a) light pass = poll only the store, full pass (ring + mesh) every 8th iteration, switch `--knet-loop-slim`; (b) TSC loop clock accepted on KVM guests (the guest hides the invariant-TSC bit, so `fastclock` fell back to `clock_gettime` on the lab VMs).
A/B (daos VMs, prof builds main 72ffa69 vs branch b652606, 2 rounds alternating, `loop-ab.sh`, `ab-table.sh`), CPU us/op / p50 us: s1-r4k1 168.3/265 -> 183.4/287, s1-w4k1 181.9/244 -> 194.9/267, s1-w4kq16 85.1/545 -> 98.9/623, r3-r4k1 180.4/274 -> 173.8/270, r3-w4k1 430/573 -> 432/565. Worse on s1 (>= +7 % CPU, +9 % p50): rejected. The isolation run (slim 0, TSC only) produced no data (block output empty), so TSC alone is untested.
Classifier fix (same day): `classify.awk` now strips turbofish generics (`step::<Nvme<.., store::dev::MonoClock>>` made every loop frame "store_commit") and puts poll/pump/clock leaves in `poll_loop`; stage-profile-20261016 csv/tables regenerated (s1-r4k1 nv-kernel: store_commit 5.4 s -> 1.8 s of samples; per op store_commit 49.6, poll_loop 40.3, pg_exec 46.3, rx_decode 25.7 us).
Next lever for CPU/op: park more of the wait (needs a wake source with less overshoot than a ring timer), not loop cost.

## Am. 2 (2026-10-18): default park 10 %, was 25 %
Finding (ice-b VMs, SPDK, s1, `kvnme-gate` r4k-q1 + 3-round A/B): the 25 % park lost 4K QD1 reads against BlueStore (iops 0.85-0.90x BS in two gates; kernel-NVMe 1.05x). Per-stage stamps (prof build, `LATREP`): the loss is inside `pg_in->reply` (PG core exec + store read) p50 182 us (park 25) vs 115 us (park 0); every other segment is equal (rx, xcore hop, reply tx). A ring-timer park costs a wake (guest halt exit + timer interrupt) that is roughly constant per park in these VMs and is paid on the latency path; the 25 % value came from ice-a, where the wake is cheaper.

Change: default `STORE_PARK_PCT` 25 -> 10 (`--knet-store-park`, `NV_KNET_STORE_PARK` unchanged). Open (90-open-questions, OQ 117): the constant 10 % is a workaround; the park must never lose to BlueStore (derive from measured wake cost or drop).
Siblings: kernel-NVMe backend uses its own `--knet-store-irq-park` (completion interrupt wakes the core, unaffected); DPDK/AF_XDP tiers never park (poll mode); replicated/EC and crc/secure do not touch the wait loop.
