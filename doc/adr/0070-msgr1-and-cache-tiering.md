# 0070 msgr1 (v1 wire protocol) and cache tiering: parity decisions
Status: superseded by adr 0168 (msgr1 OUT, cache tiering OUT; the cache-tier safety floor stands as in 0168 decision 3)
Date: 2026-10-12
Context: adr 0013 listed both out of scope for v1. Mandate 2026-10-12: 100 % functional parity with classic except Lua.
## msgr1
Facts (verified in tree): classic `ms_bind_msgr1` default true and `ms_bind_msgr2` default true: every classic OSD/mon in main still binds BOTH and advertises an addrvec with v1+v2 entries; no deprecation. The osdmap carries our addrvec: if we advertise only v2, a v1-only client sees an OSD without a usable address (hangs on that PG, no fallback).
Who needs v1: (a) kernel rbd/cephfs clients without msgr2 (libceph msgr2 landed in kernel 5.11; enterprise kernels older than that unless backported: RHEL/CentOS 7 (3.10) and 8 (4.18, verify per minor release), Ubuntu 18.04/20.04 GA 5.4, SLES 15 SP2-); (b) librados/librbd older than Nautilus (14.x) clients, old QEMU/libvirt builds, old Proxmox/OpenStack hosts; (c) ceph-fuse/rbd-nbd of those releases. Those clients are common in croit-style long-lived enterprise estates; modern clients all speak v2 (v2 preferred, tried first).
Cost: v1 is a small protocol (banner + addr exchange + connect/reply tags with cephx authorizer, per-message header/footer with crc32c, ack/keepalive tags, lossy/lossless policy, reconnect with seq). Own spec from ceph/src/msg/async/ProtocolV1 behaviour; no secure mode (v1 has no encryption; cephx signing optional `cephx_sign_messages`). Message bodies are the same encodings we already have; only framing/handshake/auth differ. Estimate 2-3 engineer-weeks incl. tests; risk: low-medium (reconnect/seq semantics, authorizer v1 with cephx ticket verification we already do for v2 auth_bytes).
Decision: IMPLEMENT, default ON when built (honour `ms_bind_msgr1`, default true like classic), as its own crate module behind the same connection trait; DPDK TCP stack serves a second port (6800+ legacy range, v1 addr type `legacy`). Interim: until G3 lands croit-flashstore-osd advertises v2 only and the docs/migration list "clients without msgr2 unsupported". Perf: v1 clients get crc/no-secure mode only, same zero-copy payload path. mon `mon_osd_...` nothing to change. Verification: kernel client from a v1-only box (CentOS 7 / 3.10 or `ms_mode=legacy` mount option), librados nautilus 14 client in container, mixed with classic OSDs.
## Cache tiering and hit sets
Facts: docs (`ceph/doc/rados/operations/cache-tiering.rst`, reference submodule) state tiering was deprecated in Reef and "lacked an active maintainer ... do not deploy new cache tiers", migrate away. Upstream keeps the mon commands (osd tier add/cache-mode/...), pool fields and hit_set pool opts for existing clusters. Real deployments on current main are rare and heading to removal.
Decision: DO NOT implement the tiering agent (promote/flush/evict, hit sets, PG_HITSET_LS/GET, proxy ops, `cache-flush/evict` ops, tier-specific stats). Compat floor (cheap, G4): a PG whose pool has `tier_of` / cache_mode != none must not confuse classic peers: croit-flashstore-osd answers ops on a cache-tier pool as a plain pool in cache_mode none semantics only if the pool is `none`; for an active cache_mode, treat as UNSUPPORTED pool type = fully passive (prime safety rule) and log once. Revisit only if upstream undeprecates or a paying customer needs it; then it needs hit-set persistence (pgmeta objects), agent, proxy ops: large (months), parity.md row stays `oos (upstream deprecated)`.

## Amendment 1 (2026-10-25): msgr1 is OUT
The msgr1 decision "IMPLEMENT" and the G3 backlog item were reversed by adr 0168 (msgr1 OUT, accepted risk): croit-flashstore-osd advertises v2 only; v1-only clients are unsupported. Cache tiering stays not implemented (same as here); only the passive-pool safety floor applies.
