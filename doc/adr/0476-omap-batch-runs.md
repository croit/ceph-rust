# 0476 Omap batch runs: a batch is one sorted unit end to end, ordering off the commit core

Status: accepted, amended (am. 1-11, N?; consolidated 2026-10-25, history: doc/perf/adr-0476-history.md) (user decision 2026-10-21; format default since am. 1: doc/perf/omap-runs-20261022.md; compaction am. 2: doc/perf/omap-runs-compaction-20261023.md; open steps: doc/perf/omap-batch-runs-handover.md)
Date: 2026-10-21
Amends: 0021 (S2 WAL/replay, S5 tree, S9 omap); builds on the write-buffer spike (branch c8947bc, rejected, unmerged)

## Context

omapbench populate (rep3, one object, 1024-key `omap_setkeys`): BlueStore 1.32M keys/s, croit-flashstore-osd main 167k (zen4, scale 1). Measured (doc/perf/omap-perkey-20261021.md): the store is 85-90 % of the one core that carries the PG on the primary AND on each replica (5.3 us/key); three cores idle. Per key: 3 tree descents (~2.6 us), same-core checkpoint of ~0.35 dirty 8 KiB leaves (~1.3 us), batch exploded into per-key objects at every layer (~0.3-0.4 us). The write buffer branch removes the descents but inserts every key into one shard-wide ordered map (0.5-0.75 us/key at 1M keys, any ordered map) and merges on the same core (store bench 457k at 1M keys, ~200k once full). Measured baseline: BlueStore spends 2.1 us/key in total over 4 threads. Own target, derived from the owning-core budget: 2M keys/s per PG = <= 0.5 us/key on the owning core end to end.

## Decision

- A client omap batch stays one unit from the wire to the WAL: `omap_setkeys` indata (Ceph map encoding) is kept as the borrowed message buffer, validated once (strictly ascending keys, key length limit; 15 ns/key); non-canonical input (unsorted, duplicates) is normalized once with the map-decode rule (last value wins). The PG txn op, the repop (identical encoding: copied as a block), the replica and the store adapter carry the blob, never per-key owned pairs.
- Store: a batch of >= `run_min` keys (default 64) on a pool object (not pgmeta, temp or an EC stash generation) is one record op `RunPut{obj, blob}` written as received (one copy + crc into the WAL unit). No tree access, no staging map, no per-key record op, no per-key allocation. Smaller batches and single-key writes use the write buffer B (the write-buffer spike, branch c8947bc) or the tree path.
- In memory a run = lsn, object id, blob (refcounted WAL-unit copy), entry offsets (u32), bloom filter (10 bits/key, blocked: one 512-bit block per key, am. 2; a lookup hashes the key once for all runs of the object and tests all its bits without an early exit, am. 15). Per object: run list, oldest first (order lsn). Removals (am. 5, N?): a removal batch staged as a run is a run of removal entries (empty value record, adr 0647-omap-blind-removals); other removals are tree ops that kill the run entries of their keys; clear / remove drop the object's runs.
- Reads (get, list, range, header-independent): B, then the object's runs newest first (bloom, then binary search; a removal entry: absent, no tree lookup), then the tree. A scan steps the merge of the object's runs alongside the tree scan and emits both in key order without copying entries (a run entry replaces the tree entry of its key; the page cut copies one key; runs a merge in progress retired start past the retired key prefix instead of walking its dead entries) (am. 9). Read-your-writes from the first acked lsn as today (runs are visible from apply).
- Run count (am. 2): bounded by compactions, not by tree merges. A compaction is an in-memory k-way merge of adjacent runs of one object into one run (newest wins, killed keys dropped, a removal kept over the older entries of its key; no WAL record), built on the owner core in slices (4096 input entries per poll and compaction, several compactions on disjoint windows of runs) from clones of its inputs (shared entry buffers; a pure function of them) and swapped in only when the inputs are still the object's runs (kills since its start apply to the result: the retired key prefix of a merge in progress dies in bulk, the other kills are looked up (am. 9)). A compaction whose input left (merged, cleared, every entry killed) or was replaced is dropped at the owner's next compaction step instead of being stepped to its end (am. 12): its output and the inputs only it holds return at once and its object is checked again (as after a swap-in), so compactions hold no memory beyond the live runs; a job out on a helper is dropped when it returns. Policy: the oldest `run_fan` (default 4) adjacent runs of the lowest size tier (entries in `[fan^t, fan^(t+1))`) that holds that many (about `fan - 1` runs per tier remain); at `run_max` (default 24) runs above the barrier of the object's tree merge in progress (its order lsn cutoff; all runs without a merge) the `fan` adjacent such runs with the fewest entries, and a further batch of that object waits for the compaction (blocking callers take the tree path). Runs taken by a tree merge in progress are not compacted and do not count toward `run_max` (am. 11: they leave as the merge's slices retire them; counting them made new batches wait for the whole merge and forced cross-tier compactions, doc/perf/bfill-rate-20261026.md).
- Durability = WAL floor (as the write-buffer spike, branch c8947bc): ring units holding live run records are released only after the run reached the tree. A compacted run keeps the parts of its inputs (order lsn, record lsn, re-log WAL bytes, live entries) and per entry its part (am. 2): the floor index holds the parts with live entries; a re-log writes one part's live entries under its order lsn and moves the part to the new record; an entry shadowed by a newer input or killed leaves its part, a part without live entries leaves the floor. Replay rebuilds the runs as logged. Tree merge on the owner core of all runs of the object holding the floor, deferred while the run memory budget (shared pool) has room; triggers: soft size, ring floor, a user txn refused for the runs' page charge (one merge; while a running freeze holds back the meta growth the txn waits for the checkpoint instead, am. 2), idle (per object: an object without a new run for one to two checkpoint intervals merges while other objects keep logging runs; marks advance on every poll, am. 2), explicit drain. A merge of a run holding m keys into a tree of L leaves writes each touched leaf once (k = m / L keys per dirtied leaf).
- Blind tree ops (am. 5, 13, 15; adr 0647-omap-blind-removals): the store keeps no omap counters, so no omap put or removal is looked up for an old value (objects with fragmented / data-block values free them key by key). A removal batch (`OmapRmKeys`) of at least `run_min` distinct keys that may be a run (as a put batch) is staged as one run of removals: no tree access, no kill at commit; the merge removes the keys (am. 16). Another removal batch of an object without such values is staged as one ascending list of its distinct keys (am. 13): a key the txn touched before (put, removed, range-removed, in a staged run) is removed in the txn's own view, the others join the txn's blind removal list (`Op::Del`, emitted first, ascending), one sorted key list without an overlay entry per key; an object whose omap the txn has not touched is checked once per batch. A record's ascending stretch of tree ops kills its run entries in one batch, run-major (am. 15; replay alike): per object, each run takes all of the stretch's keys of that object in two passes, bloom and the run's index integers first (each key's first candidate entry), then the candidates' key bytes (loads independent of each other). Prepare and apply probe each ascending stretch of a record's puts and removals through one sorted leaf cursor: a key past the leaf's fence routes from the deepest page of the cursor's path that holds it, each interior page routed once (child and fence from the same walk of its restart group, no fence copy per key). WAL tags 6 / 7 of earlier builds (`DelCounted` / `PutCounted`) replay as plain `Del` / `Put`.
- Range removal (am. 5): a tree range delete (no interior leaf loads, no count); it kills the live run entries in the range.
- Ring liveness (am. 1): a run has an order lsn (newest wins, merge cutoffs) and a record lsn (the floor). Under floor pressure (`ring_full_by_floor`) the live runs of the ring unit holding the floor record are re-logged in one record (`RunPut` with the order lsn set; replay replaces the run of that order or inserts it there), once per checkpoint. The `RunPut` encoding always carries the order lsn, so a re-log never takes more ring than the unit it frees. Ring reserve: client and sys txns keep two units plus `relog_blocks` (one unit, or the largest live run record's chain), merges keep `relog_blocks`, re-logs keep nothing; a run is staged only while the ring part above the checkpoint threshold holds five units plus twice its `relog_blocks`. A run whose entries are all killed leaves at once. A record logs at most one new run per object (the floor index is per (record, object, order)). Merge slices are sized by the admission's own page bound per entry (at least one entry whenever a single put fits).
- Run memory (am. 1): a store formatted with runs takes the run hard size (twice the soft size, soft = 1/16 of the shard share) out of the cache share at mount (`carve_runs`: pages, dirty marks, point cache and delta cap scale down together; the cache keeps its 4096-page floor, the run budget gives way below it). Run memory = the runs' buffers plus each compaction in progress as allocated (its output is reserved at its inputs' bytes at the start; am. 12) plus a helper job's reservation: the soft size (merges pressed) and the hard size (no new run admitted) see everything runs and compactions pin. Run room is the device's run pool (per-core stores of all cores are members): a txn parked on run room is retried when any member lowers its run bytes (`RunPool::freed` in the parked queue's progress marker), not only on its own shard's IO (am. 14: otherwise it waited for its shard's timed checkpoint, ~5 s, doc/perf/omap-combo-stall-20261030.md).
- Merged values (am. 1): a merge stores plain values of at least `val_comp_min` bytes compressed with the loaded value dictionary of their class (else the shared one) when that saves 1/8 (the stage's rule); tries follow the stage's adaptive sampling per class (adr 0021 am. 58/59: after n misses in a row the next 2^n - 1 values, n <= 6, are not tried; a hit resets), with the shard's own sampler for merges (the stage keeps its own), kept across merge records and slices (am. 10; before: 4 misses per merge record, which a time-capped slice reset: 227k-622k tries, 0 hits per 1M-key fill, doc/perf/bfill-rate-20261026.md). No dictionary loaded: plain (a replay may store either form of the same value).
- Format (am. 1, am. 2): runs are the only omap format: mkfs sets `FEAT_OMAP_RUNS` (with `FEAT_OMAP_COUNTERS` / `FEAT_OMAP_BLIND`, whose counters no build keeps since `FEAT_OMAP_UNCOUNTED`), the daemon refuses a store without it (`FEATURES_REQUIRED`, re-mkfs). `FEAT_OMAP_TOMBS` (mkfs and every mount, am. 16): run entries may be removals. Small batches and single keys take the tree path (part of the design, not a format variant).
- Merges (am. 1, am. 9): k-way merge of an object's runs by one linear pass over the active run heads per output entry (newest among equal keys; a removal deletes the key from its leaf, a leaf without the key stays clean (am. 16); the run count is bounded by `run_max`, a heap cost more per entry); a slice refused for missing pages waits for its reads (queued wants included) and is resubmitted as built; merge apply moves entries without a copy. A slice's merge positions are computed once by the slice sizing and reused by prepare and apply while the run set is unchanged; its ascending keys go through a leaf cursor (one descent per leaf) (am. 2). Each non-final slice retires its key range at apply and in replay: the entries of the merged runs (order lsn <= the merge's cutoff) in the slice's range are killed (parts without live entries leave the floor, a run without live entries leaves), so live entries and the WAL floor follow the merge; the inputs' run memory returns at the last slice (rebuilding half-dead runs copied their live half in one owner-core step: commit max x2-4, rejected) (am. 9).
- Merge apply and compaction cost (am. 4): a merge slice's entries below one leaf's fence are merged with the leaf in one rebuild and cut into the fewest pages (full pages for an append at the right end, else balanced), split off right to left; a leaf with one new entry takes the single put. A compaction steps one pass over the input heads per output entry (newest among equal keys, the others skipped by a bit mask; at most 64 inputs), copies each entry once as encoded; omap key compares (compaction, merge heap) and bloom hashes start past the object prefix shared by all keys of a run. Helper cores: adr 0534 (dispatch unchanged).
- Blocking barriers (am. 4): a parked txn retried inside a blocking queue barrier (`Store::drain_queued`) never waits for run room (`run_max` compaction or merges): it takes the tree path, since nothing else runs on the core meanwhile.
- Maintenance pacing (am. 3, am. 8): a background merge (object written; no drain, page charge, ring or run-room trigger) is paced by the writes: it moves one entry per run entry admitted since it began (`RunSet::admitted`, re-logs not counted), in slices of `MERGE_SLICE_NS` (`merge_time_cap`) while behind and the pool is over its soft size, none while ahead or below it; ahead with an empty pipeline (no other txn, nothing admitted since its last slice or paced wait) it takes one such slice; a shard with a runnable merge slice stays active (`Shard::quiet`); a background merge stops at the shard's `dirty_soft` mark and waits for the checkpoint, merges a limit waits on keep `dirty_hard` and force a checkpoint there (am. 7); a run refused at the checkpoint ring threshold triggers a merge; compactions share one `COMPACT_ENTS` budget per poll, smallest first, and build bloom and per-entry part while stepping (swap-in O(parts + kills)); compaction and merge run after the poll submitted the client WAL unit. Meta growth for a run page charge also runs during a freeze (adr 0021 am. 68; the data-region claim `run_claim` is removed, am. 7). A range removal's prepare skips the runs of objects it clears (O(runs)).
- One path for replicated and EC pools (EC omap = the same store txns), SPDK and kernel NVMe tiers.

## Rationale

- A sorted batch already is a sorted run: indexing it costs 15 ns/key versus 500-750 ns/key for any per-key ordered insert at 1M keys; the commit path keeps only byte work (~40 ns/key: receive, crc, WAL copy, two replica copies) plus per-batch constants.
- Merging immutable runs needs no ownership: it is the only per-key ordering work and it can run on the three idle cores (k-way merge 180-290 ns/key with copies; less with value references).
- Expected owner-core cost per key: primary ~0.15 us (msgr + crc 0.05, op validate 0.02, repop copies 0.02, WAL copy + crc 0.02, run register + bloom 0.03), replica ~0.1 us; tree merge ~0.2 us amortized when k >= 10, deferred while runs fit memory. Burst >= 2M keys/s per PG core, sustained bound by the tree merge.
- The tree stays the one persistent index (no second on-disk structure, no compaction format, no read amplification once merged).

## Consequences

- + Commit path per key independent of object size; no dirty page per key; no ordered insert on the commit core.
- + Uses the OSD's idle cores for the only per-key ordering work.
- + Batch encodes / decodes as blocks on primary and replicas (~0.3 us/key of per-key materialization removed).
- - On-disk format: WAL op `RunPut` (`DelCounted` / `PutCounted` of earlier builds replay as plain ops); replay rebuilds runs above the floor (bounded by the ring).
- - A put batch of blind puts loads its leaves in the record's prepare: a txn whose distinct page set exceeds the txn page budget (cache / 2) is refused there (before am. 5, the stage's lookups had loaded them and a fully resident set passed).
- - Point gets on objects with unmerged runs: up to `run_max` (default 24) + 1 bloom probes and binary searches, up to 2 x `run_max` + 1 while a tree merge of the object is in progress (am. 11); `run_fan` (default 4) sets the compaction fan-in.
- - Run memory comes from the cache share (pool shared by the device's stores).
- - Cross-core merge jobs: a new owner/helper protocol (immutable inputs, generation check on return).

## Alternatives

- Write buffer B as the only mechanism (branch): per-key ordered insert 0.5-0.75 us + same-core merges; measured ceiling < 0.5M keys/s.
- Persistent sorted segments per object (LSM tier, compaction on helper cores, tree for small omap only): lowest owner-core cost for sustained loads beyond the run budget, but a second persistent index, compaction format, segment space accounting and read amplification; kept as the next step if the tree merge bounds sustained rates.
- Per-key hash index for point gets instead of blooms: one cache miss (~0.1 us) per key on the commit core; blooms + bounded run count keep the commit path at per-batch cost.
- DAOS-style (study, ideas only): WAL-only commit + background checkpoint (croit-flashstore-osd already persists pages only at checkpoint, COW), sub-page dirty tracking and byte-range redo (cut checkpoint bytes, not per-key CPU), small nodes (less memmove, more depth), descent reuse across a sorted batch (random keys of a 1024 batch land ~80 leaves apart in a 2M-key object: saves upper levels only). None removes the per-key descent on the commit core; sub-page dirty tracking stays an option for the tree merge's page writes.
- Smaller pages / sharding one object over cores: changes ownership of one object, breaks per-object ordering.
- Range tombstones (part of the original removal design, never built): a range removal is one tree range delete without leaf loads (am. 5). Runs of removals, rejected in am. 5 for the exact counters (each removed key's old value), are built since the counters are gone (am. 16).
- Run values staged in tree record form (dictionary-compressed in the stage's batch loop, merges carry them; 2026-10-25, rejected): merge CPU per entry -15 % in the store bench, but the compression moves onto the commit path of primary and replicas (b-fill OSD CPU +20 %) and every get / list / fetch of a run entry decompresses (b-mix put p99 1.5-1.75x, fetch_dir 2x on ice-a); doc/perf/bmix-merge-20261025.md.
- Blind kills key by key, each run searched forward from the previous key's position (OQ 109, doc/perf/omap-txn-cost-20261026.md; replaced by am. 15): per key and run a bloom test with a branch per bit, and the run holding the key searched with its key bytes read inside the gallop, a run-buffer miss the next key's search waited for; 1.9-2.3x the cost per removed key of the run-major kill (doc/perf/omap-killasc-2026-10-30.md).
- Removal batches of several txns of one object probed and killed in one pass (am. 13, rejected): ties completion across clients and adds grouping state; the cursor route within one batch shares most of the walk.

## Open questions

- `run_min`, `run_max`, `run_fan`, bloom size, run budget share: tune by measurement.
- Compactions on helper cores (they are pure functions of immutable inputs with a swap-in check): rt cross-core messages (XMsg) or a dedicated job ring; CPU placement next to the NIC IRQ rules. Not built: compaction is 15-20 % of the store CPU of a populate (doc/perf/omap-runs-compaction-20261023.md).
- Tree merge of very large objects beyond the run budget: k falls with object size; persistent segments (alternative 2) if the sustained rate falls below target.
- Scans with many runs (RGW bucket listing shape): merge cost per returned entry; measure list128/list16k against BlueStore.
- Scans must not pay for runs of other objects: the buffer branch's shard-wide merge per scan cost +50 % scan CPU and 18-40 % of B point ops on the cluster (doc/perf/omap-perkey-20261021.md); per-object run lists keep the scan of an object without runs on the tree path alone. Gate: B point ops and list16k against main.
- Commit latency of small writes on a core saturated by long scans (A point ops in the ab mix, ~4-7 ms per read/write alternation vs BlueStore 0.4 ms; open bug, OQ 120): op scheduling between scans and writes, independent of this decision.
