# 0078 Resumable data reads beyond the prefetch window
Status: accepted, amended (am. 1)
Date: 2026-10-13
Context: ADR 0043 prefetch is bounded by queue room and 32 MiB per shard. The executor warms at most 4 MiB; larger/fragmented reads fall through to synchronous batches of 16, blocking every PG on the core. Retrying after one batch without preserving the result would reread the consumed prefix. A request can also read several ranges: earlier successful reads must survive a later refusal.

Decision:
- Keep the fully prefetched direct-copy path. Unprefetched non-blocking `read_runs_into` creates a continuation keyed by request session, physical runs and destination length. The executor supplies connection/tid and releases its session when the run finishes. A refused run keeps every range of its request, also those it did not reach (am. 1); ranges a retry no longer asks for (relocated extents, changed snapshots) expire after the 200 ms idle TTL. Direct store callers consume completed results immediately.
- `pump_at` copies each completed DMA read with its block CRC and immediately submits more reads. At most 8192 blocks (32 MiB) of rolling DMA per shard, including commands of discarded continuations; leave queue slots for writes. At most four admitted request sessions per shard. Capacity waits and data waits remain non-blocking even after the metadata scan retry bound; the executor's stuck detector (am. 1) is their only bound.
- Result storage is at most the sum of the physical read destination sizes of the four admitted requests, in addition to their ordinary caller/reply buffers and the existing prefetch table. It scales with requested output, not number of outstanding device commands. A resumed range copies its retained result to the caller; this costs a second data copy on the rolling path. Small fully prefetched reads keep their original single copy.
- Pin the reader epoch before yielding with a physical snapshot. Release the snapshot pin when the request finishes or its unused continuation expires. Submitted reads keep their ordinary per-command pins independently. Expired commands remain charged against the DMA bound until completion; late completions are discarded. Idle continuations expire after the existing 200 ms prefetch TTL; in-flight reads are allowed to finish even on slow devices.
- Gate warming recognizes ranges already owned by a continuation, preventing repeated prefetch of a consumed prefix. The actual read re-resolves extents and validates the returned physical block CRCs as before. No disk or wire changes; write durability/WAL semantics unchanged.

Consequences: reads yield instead of waiting for device latency; rolling refill removes batch barriers on the client path. Additional retained result memory/copy for reads beyond prefetch, and snapshot pins can delay reclamation. Cancellation without a final executor callback is reclaimed by expiry; an abandoned in-flight read may finish its bounded request before expiring. Offline blocking callers retain their existing synchronous helper.

Tests: store `a_large_read_yields_without_waiting_for_a_batch`, `rolling_ranges_survive_a_multi_read_request_retry_and_expire_after_cancellation`; existing prefetch error, overwrite, CRC, compression and crash suites. Local debug simulator benchmark `perf_rolling_read_stall`: 12 MiB read after 4 MiB warming, core device stall 2,830,550 -> 0 ns. No hardware throughput claim.

Amendment 1 (2026-11-02, omap-held-stall): a refused run kept only the ranges it had touched. A run stops at its first refusal, so it dropped the reads of later ops; a compound read whose omap value listing completed in one run and started over in the next (the scan memo ends with the listing) re-read one value per run while the run dropped the next one, and never finished (lab case 36: `ceph_test_rados` compound reads parked for 300 s, ~1000 runs/s, `released` ~= `parked_scan`). Decision: (a) `ShardStore::read_session` keeps every read of a refused request; untouched ones expire after `PF_TTL_NS` idle, the request's end releases all. (b) Executor stuck detector (`opexec::Engine::refusal`, `SCAN_STUCK_NS` = 30 s): counted from an op's first refused run, kept across re-parks; an op still refused 30 s later runs blocking next and prints `WARNING TIMEOUT refused op runs exceeded 30s` (refusals that claim progress, data waits and listing slices, are not counted by `MAX_SCAN_TRIES`). Evidence: doc/perf/omap-held-stall-20261102.md. Regressions: store `scan::a_cold_compound_read_finishes_without_reading_a_block_twice`, opexec `wake::an_op_refused_with_progress_runs_blocking_30s_after_its_first_refusal`.
