# 0040 EC rollback and stash persistence (shard role)
Status: accepted
Date: 2026-10-10 (amended after implementation, same day)
Context: adr/0039 phase A2. A classic EC primary makes writes visible only after all shards commit; a shard that is ahead of the authoritative log after a failover must roll its divergent entries BACK (stash objects keep the old bytes, spec ec.md 7.5/7.6, pglog.md 7.3 case 4). Replicated PGs set `can_rollback_to == rollback_info_trimmed_to == head` always (pglog.md 6.5); EC needs both real and persisted.
Decision:
1. Log cursors: `can_rollback_to` (crt) and `rollback_info_trimmed_to` (rit) are real for EC PGs and persisted in the existing `_loghead` triple. Store ops (peering::store): `LogAppendKeep(entries)` = append, head := last, crt/rit untouched; `LogCursors{can_rollback_to, rollback_info_trimmed_to}` = ABSOLUTE set of both (later op in a txn wins); `Shard(Vec<ShardOp>)` = shard-object mutations at a generation (Remove, Rename, Truncate, SetAttrs(None = rmattr), CloneRange). ShardOps are no-ops on missing sources so rollback/roll-forward can be re-run after a crash. Replicated PGs keep `LogAppend`.
2. mod_desc bytes are stored verbatim; interpreted only for roll-forward and rollback (`ec::moddesc::parse`, executor `peering::ecroll`). Records: ec.md 8.1.
3. Roll-forward (stash deletion of entries in (rit, X]; then crt, rit := max(., X)) runs, in the same StoreTxn as the log update, when: `pg_committed_to` > crt on a sub-write or dummy roll-forward op (only if the transaction was applied), the log is trimmed (entries leaving the log first give up their stash; crt/rit raised to the trim point), an object is recovered (push complete, `recover_got`), and the PG is deleted (remove_pg deletes every generation). Stash generations = DELETE/TRY_DELETE version, ROLLBACK_EXTENTS generation (v3: only if our shard is in some extent's set).
4. Rollback executor in the sans-IO PG (`rewind_divergent_log_ec` / `merge_log_ec`, case 4 after cases 1-3): applies only when EVERY divergent entry of the object is `can_local_rollback`, parses, and has version > max(auth log crt, our own crt before the rewind clamp); entries newest first, records in reverse order (ec.md 7.6 table) emitted as `ShardOp`s plus a SnapMapper op for UPDATE_SNAPS; missing set untouched. Otherwise case 5 (remove object, missing at prior_version), which re-fetches the object: always correct, only slower. Objects removed outright (cases 1, 2, 5) also delete the stash of their divergent entries.
5. merge_log (activation with entries) on an EC shard: appended auth entries have no local stash, so crt := head while rit := min(old rit, cut) keeps the cleanup debt of our older entries; a backfill target adopts the auth log with crt = rit = head.
6. Unparsable / unknown mod_desc at roll-forward: error counter, stash may leak (no abort, no quarantine); at rollback: case 5. Stash GC at activation (amended): every stash generation not referenced by an entry > rit is removed (lists the whole PG collection: O(objects) per activation).
7. Durability: stash creation is part of the primary's transaction (applied verbatim); our reply (`committed`) is sent only from the store commit callback (adr 0008). A transaction naming an object of another shard is refused before anything is logged (no reply).
Consequences: + divergent shards converge without full object recovery. + crash-safe (idempotent ops, one atomic txn with log/info). - extra log cursor bookkeeping in plog/pg paths for EC only. - ShardOp translation per store (MemStore, storeadapt).
Alternatives: always case 5 (current replicated behavior; rejected: re-reads whole objects, and a classic primary expects shard rollback so peering finishes without data movement); cleanup journal separate from the log (rejected: crt/rit already encode it); quarantining the PG on unparsable mod_desc (rejected for rollback: case 5 is a safe fallback).
