# 0084 Destination-aware input, ordered mesh lanes, split client/peer windows, sender repop credits

Status: accepted, amended (am. 6); `flashstore_repop_credit` (am. 4) default off
Date: 2026-10-13
Consolidated 2026-10-19; full pre-consolidation text: git show 60868596d:doc/adr/0084-shard-aware-input.md

## Context

A store admission check over all shards stopped every connection and the whole cross-core inbox when one shard was congested. Removing it without bounding actor-retained work would move the queue into replica replay, future-map messages and op engines. A shard window shared by client writes (held until replica acks) and peer repops can deadlock a peer link. Measurements: doc/perf/codex-perf3-2026-10-13.md, doc/perf/adr-0084-history.md.

## Decision

Destination and reservations:
- Resolve the physical destination from the store placement table. Store admission, replica cache probes and retry gates test that shard only. ADR 0082 (+ am. 1) unchanged: no store prepare, FIFO, visibility, durability or cold-barrier change.
- Reservations are allocated at startup: 128 inputs per physical shard and 64 MiB of encoded input, one oversized input up to 768 MiB (count = existing default store queue cap). Held in MOSDOp and Inbound through actor retention and retries. Fanout clones share a slot; moving/cloning an envelope does not return its reservation. Slot refs and accounting use bounded atomics, no per-reservation allocation or lock (extends ADR 0006's SPSC-only shared accounting; PG, connection and store state stay core-owned).
- Windows are split by class (am. 2): `input_credits(shards)` = 2 x shards windows; client data uses window/lane `s`, peer data window/lane `shards + s`, peer controls lane `2 x shards`. Same bounds per class (up to 64 MiB / 128 inputs per shard each). A peer link never waits on capacity held by work that waits for that link; index arithmetic only.
- Peer controls: separate 32-input window per connection core, same byte rules; data cannot consume it. A connection retains at most one decoded input awaiting admission and cannot expose its next event until it is accepted. Retry heads by physical shard; pump buffered messenger events right after a successful retry; rebucket unadmitted input at placement changes.
- Raw peer relays: private 32-fragment window per connection. Authenticated Incoming messages carry the final fragment's reservation and charge their whole retained payload. Already-reserved relay controls reach their actors despite unreserved input on another connection. One received fragment may wait locally if a concurrent frame charge closes the window; forward it before socket closure. A relayed connection's whole receive batch (<= 1 MiB, `recv_chunks`) is ONE fragment (`OsdNet::drain` -> `Osd::on_relay_bytes`, no copy; am. 1, was one TCP segment per `pipe_rx` on DPDK). Decoder frame/segment limits, transport buffers and partial frame storage still apply outside the windows.

Lanes and ordering:
- Each core pair has physical-shard data FIFOs, a separate raw-relay FIFO, an ordered control FIFO, a fenced output/progress FIFO, an independent statistics FIFO. Physical data rings only towards the shard owner. Controls and progress have capacity data/relay cannot consume. Generations and lane ordinals are stamped before the source outbox; ordered controls snapshot every preceding non-statistics lane incl. unsent messages; later messages wait behind that generation. Peer interval/lifecycle messages create barriers; completion and lease messages stay fenced by barriers. Unsent statistics coalesce to the newest.
- Port backlogs: 32 envelopes per physical data lane, 128 per ordered lane, 64 per output/progress lane, 2 statistics envelopes; preallocated, only occupied send lanes visited. Legacy single-ring interface keeps its 16 Ki-envelope backlog. Inbox burst/time budget unchanged.
- A raw mesh pop is not actor acceptance while its pipe retains raw or decoded input. Ordered controls wait for that prefix to reach its actor, not for durability. Reserved capacity never bypasses an ordering dependency. Kernel receive leases keep byte order across pause/resume and late completions. Own TCP retains the unread suffix of at most one 1 MiB receive batch per connection and checks readiness between chunks.
- Kernel receive pauses cannot consume the whole provided-buffer ring: once half its buffers are retained, further paused completions are copied into a preallocated spill pool (same fixed byte capacity as the provided ring, default 32 MiB per core; held-record capacity 2 x buffer count) and the original buffers returned. Normal input keeps the no-spill path. Overflow storage full: keep the original lease until cancel/resume; never discard bytes. Submission-queue retries: five-second hard timeout.

Sender-side repop credits (am. 4; `flow.rs`, PG core, no locks; switch `flashstore_repop_credit`, default false = am. 2 behavior everywhere):
- Per (peer, physical shard) budget of repop (`MOSDRepOp`) and EC sub-write bytes + count in flight. Shard = the sender's `input_shard(pg)` (equal store shard counts across OSDs of a pool; a differing placement only costs the guarantee). Charged at the PG's `pg_send` after encoding (payload ropes counted); released by the reply with the same key, or when the sending PG aborts the request (am. 5): a new interval or a merge ends every sub-write still unanswered and the PG reports exactly those (`Action::SubWritesAborted`: peer, shard, tid), their credits return and their waiting requests are dropped, never sent; a peer down/restart is such an interval change. After a map, credits of PGs that left the core return too. No expiry timer. The replica discards a request of an older interval by its `map_epoch` only (classic `can_discard_replica_op`, peering.md 7.3): a request it drops unanswered is always one whose primary saw (or will see) the new interval and aborted it. Key = (peer, spg incl. shard, tid): repop = header tid, EC request = destination spg, EC reply = pgid.pgid + `op.from.shard` (tids count per PG; EC acting `[a,b,b]` shares a tid across two shard positions).
- Over budget: FIFO per lane in the PG core (bounded by client admission), later writes of the lane queue behind it (order kept); an empty lane always admits one message of any size.
- Per-PG order (am. 6): a held request holds every later message of its PG to that peer (UpdateLogMissing, lease, trim, info, recovery, EC sub-read, a request sent after the switch went off) behind it in the same lane FIFO; such a message leaves uncharged right after what precedes it. Held per (peer, pg): lane + count. Not a PG message (no spg: MOSDPGRemove, Create2): never held. An abort drops the PG's waiting requests only; the messages behind them still leave in order (the replica discards an older interval's message itself). Other PGs, other peers and classic peers are not delayed. Reason: a replica appends in arrival order; an UpdateLogMissing (lost.rs, `mark_unfound_lost`) ahead of an older held repop / EC sub-write moved its `last_update` past it, the replica dropped the request as a duplicate unanswered (log hole, the client write hung until the next interval). Sibling at the messenger: UpdateLogMissing went at priority HIGH, RepOp / EC sub-write at default; the msgr2 out queue sends higher priorities first (a reconnect, a not yet pumped batch), same reorder towards classic and croit-flashstore-osd replicas (a classic replica asserts). UpdateLogMissing now uses the default priority like Ceph (replication.md 3.2, 3.4); replies stay HIGH. Budget = receiver window / max(2, croit-flashstore-osd peers) = 32 MiB / 64 ops with one peer, floor 4 MiB / 8 ops. Only RepOp and EC Write are credited.
- Receiver (old behavior without credits: `pg_peer_in` paused the link at a repop whose shard failed `admission_ready_for`, so every later frame on that stream waited): a RepOp / EC Write from a known croit-flashstore-osd peer (`peer_nv`, osd metadata) skips the store gate (`admission_ready_for`) and lane FIFO and needs only the window reservation (+ XOUT room); it goes to the owning PG, which holds congested-store repops inside the PG (`Pg::held`, reservation retained in `Inbound`). Same in `input_can_resume`. If the reservation fails (more peers than the floor, recovery pushes, a peer build without credits, placement differences) the old hold + link pause applies: a fallback, never a drop.
- Classic or not-yet-identified peers: no credit, receive path unchanged. No new message, no wire change; knowledge per direction, one-sided knowledge is safe.
- Counters: link events `repop_credit_wait`, `repop_credit_order_wait` (a PG message held behind its PG's held request, am. 6), `repop_credit_aborted` (credits released + waiting requests dropped: aborted by their PG, or PG left the core). Perf dump `osd` gauges (detection only): `repop_credit_blocked_lanes` (lanes with requests waiting for credit), `repop_credit_oldest_ms` (age of the oldest credit out, max over the cores; grows without bound only if a credit leaked).

Tests: `placement::relay_receive_batch_is_one_fragment_of_the_window`; xcore_tests `client_writes_filling_a_shard_window_never_block_peer_acks_behind_a_peer_repop`, `many_small_omap_writes_on_one_object_never_block_peer_acks_behind_a_peer_repop`, `client_writes_filling_a_shard_window_with_repop_credits`, `congested_replica_shard_does_not_delay_other_shards_between_flashstore_peers`, `classic_peer_link_pauses_at_a_congested_replica_shard`, `many_small_omap_writes_on_one_object_with_repop_credits`, `repop_credits_of_several_pgs_with_equal_tids_all_return`, `repop_credits_of_an_older_interval_return_at_the_map`, `repop_credits_return_at_the_primary_abort_before_the_replica_answers`, `ec_reply_key_matches_its_request_per_shard`; `update_log_missing_never_overtakes_its_pgs_repops_held_for_credit` (am. 6; old code: 5 held repops discarded as duplicates); flow.rs unit tests (incl. `a_held_request_keeps_its_pgs_later_messages_behind_it`, `a_pgs_held_message_waits_behind_the_lane_requests_before_it`, `ec_sub_write_held_keeps_the_pgs_later_messages_behind_it`, `an_abort_drops_the_requests_but_sends_the_messages_behind_them`, `aborted_sub_writes_return_their_credits`, `credits_of_a_pg_gone_from_the_core_are_dropped`, `oldest_credit_is_the_one_charged_first`); peering `types::priority_tests` (am. 6), `subwrite_abort` (replicated + EC: exactly the unanswered sub-writes reported at the new interval), `pg::stale_floor_tests`; storeadapt `test-knobs` `deny_admission_shard` (dev-dependency only). Live: `lab/docker/mixed/25-event-paths.sh` P1 (croit-flashstore-osd SIGKILL with credits on under write load: `repop_credit_aborted` of the survivors grows, IO advances, clean). No network, disk or WAL encoding change; ownership metadata never serialized; authentication and durable completion unchanged.

## Rationale

Per-destination admission isolates shards; fixed ownership windows bound retained work without locks. Splitting client and peer windows removes the deadlock cause (client write reservations held until replica acks block the peer repop whose acks they await). Sender credits remove the remaining receiver-side link pause between croit-flashstore-osd peers.

## Consequences

- + a congested physical store shard no longer closes normal input for another shard; client writes can fill their window without blocking peer acks.
- - Encoded-input/queue limits, not an RSS cap: allocation overhead, partial frame buffers, caches, submitted IO and outbound lossless-session retention are governed separately.
- - One TCP stream still multiplexes destinations: head-of-line blocking remains while a peer repop waits for a congested local shard (all-classic or credit-off sets); finite buffering cannot isolate it.
- - Cold placement transitions retain pre-move reservations until that work completes; the aggregate bound stays fixed, inherited work can exceed the destination's allowance and hold capacity on its former shard. No unconditional isolation during migration or cold structural barriers (reacquiring a slot before rerouting could deadlock or reorder parked client work).
- - Credits: link core cross-core lanes (32 envelopes per data lane, `XOUT_MAX`) still back-pressure a link when the owning PG core is slow; uncredited peer data (recovery push) shares the window and can trigger the fallback; budgets per PG core, equal-S assumption.

## Alternatives

- Global store admission over all shards: stops all input on one congested shard.
- Removing admission without bounds: moves the queue into actors.
- Shared client/peer window (original): deadlocked (rented 3x1 OSD 4M hang, omap single-object hang).
- Raising the shared window to 120 inputs: only masks the count variant.

## Open questions

- `flashstore_repop_credit` is default off: validation under pressure needs the rented cluster (VMs cap at ~2 GB/s, budgets never fill); 4K QD1 A/B showed -19 % with A always first (order bias not excluded, swapped-order block not run). See doc/90-open-questions.md.
