# 0006 Runtime: thread-per-core, run-to-completion
Status: accepted
Date: 2026-10-09
Decision: One pinned thread per assigned core, busy-poll loop: NIC RX -> msgr -> op -> NVMe submit/complete -> TX. Custom minimal single-thread async executor (no tokio). PGs owned by exactly one core (hash(pgid)). Cross-core only via SPSC rings (connection core != PG core). No locks/atomics on hot path. Per-core hugepage buffer pools, no per-IO malloc. NUMA: cores + memory + NIC queue + NVMe on same node.
Multi-instance per host: each croit-flashstore-osd = own cores, own DPDK --file-prefix/hugepage slice, own NVMe, own NIC queues/VF.
Consequences: predictable latency; idle cores burn CPU (accepted; optional adaptive sleep later).

## Amendment (2026-10-09): multi-core network placement (doc/design/net-perf.md)
- NIC: one rx/tx queue per core, RSS (symmetric Toeplitz key, explicit RETA, `net::dpdk::Port::start_mq`); software predicts the queue with `net::rss::Rss`. Inbound connection -> core by hardware; outbound dials use `Config::steer` so replies land on the dialing core. Connections never migrate.
- PG -> core: `rt::route::PgRouter::core_of(pool, ps)` (stable hash, no table). Connection core decodes msgr2, routes the owned message to the PG core over `rt::mesh` (N x N SPSC; ownership moves with the value, never block on a full ring, keep a local backlog). Replies return to the connection core the same way.
- Measured: near-linear aggregate scaling to 6-8 cores in-memory, cross-core routing cost not measurable. Cross-core frees need a thread-caching allocator or pools (glibc 2x slower than mimalloc).
- Open: per-core `Osd` instances in `osd`/`opexec` (other crates), mbuf-chain zero-copy handoff (needs `Send` mbuf handles).

## Amendment 3 (2026-10-12): rx drain depth, acks per burst, inbox time budget (doc/perf/dpdk-rxdrop.md)
- `rt::Core::step` drains the NIC ring per `rt::RxRounds`: `NV_RX_ROUNDS` bursts (default 2), then, while bursts stay full, more only if `rte_eth_rx_queue_count` >= `NV_RX_HIGH` (512): as many as it holds, max `NV_RX_ROUNDS_MAX` (16). The ring is counted at most once per drain. Fixed deep drains cost a single stream 14-25 %; one burst per iteration overflowed the ring under 8 clients. No fill count (PMD) = fixed base. Kill switch `NV_RX_ROUNDS_MAX=0`.
- Pending tx (acks) leaves after every rx burst, before any PG work.
- `XPort::pump`: inbox drain bounded by `NV_XBUDGET_US` (100 us, checked after each message, first always runs; 0 = count bound only; replaced by a work slice in am. 4); all tiers (dpdk, knet, PG-only cores). Left messages stay in the SPSC rings (no loss), round-robin over source cores persists across drains.

## Amendment 4 (2026-10-18): clock reads per op; work slices replace intra-iteration time budgets
Clock classes (DAOS-style per-core cached time; fine = `fastclock`, rdtsc with invariant TSC, else `clock_gettime`):
1. Scheduling (deadlines, timers, park/sleep, aging, slow-op, store-span parking): the loop's ONE read per iteration (`now` of `Core::step` / `KCore::step` / `run_pg_core`), passed down; nothing re-reads. A ring sleep is timed by the next iteration's read (`KCore::slept`).
2. Always-on Ceph op latency counters: from the loop `now` (`Osd::now`), no read of their own.
3. Stage profiling / op-trace / phase timers: own fine reads only when on; off = zero.
4. Wake latency (`rt::wake`): a fine read only on a poke of a sleeping core and on its wake (fastclock, not `clock_gettime`).
Removed per-op reads:
- `XPort::pump` / `Osd::pump` time budgets (`NV_XBUDGET_US`, 100 us; `Osd::pump` read at start + after every event): now a learned work slice (`xcore::Slice`): work units = `XMsg::slice_work` / msgr event payload bytes, min `SLICE_MIN` 4 KiB; the units handed on in an iteration and that iteration's busy ns (the loop's read, `note_core_busy`) give ps per unit (EWMA 1/8); a drain stops after the message that fills `SLICE_NS` 100 us at that rate (first message always runs; count caps unchanged). Start / simulators: 1 ns per unit. Biased short (the iteration also polls NIC, store, tx). A fixed 128 KiB slice (1 ns/B, from 4 MiB writes) was measured first: 4K writes cost ~10 ns/B, 32 ops per drain, ~1 ms iterations; ABBA s1 w4kq32 -7 % IOPS (ice-a SPDK, 31.7/32.7k vs 34.9/34.9k), commit and reply waited for the drain.
- Per-PG busy ns (local diagnostics `flashstore_pg_*.busy_ns`): was 2 reads per `pg_run_now`, per peer message and per PG tick; now the loop's busy ns of an iteration is split evenly over the PGs that did work in it (`PgMap::note_ran` / `note_busy`, each PG listed once per iteration).
- knet store-span parking: span start, cap vs OSD timer and sleep length from the loop read (were 3 extra reads per park). A span seen at the end of a work iteration (IO submitted or completed during its work) is stamped with the NEXT iteration's read = the end of that work (the old fresh read); the iteration's own start stamp was early by its work, parks ended before the completion and the core fell into timer sleeps (r4k1 SPDK -5.8 %).
Measured before (r3 w4kq32, uprobe on libc `clock_gettime`, no invariant TSC so fastclock = vDSO): primary 11.1 reads/op (`Osd::pump` start 6.7, per event 3.0, `XPort::pump` 0.7, loop 0.6), replica 5.2; QD1 primary 20.5, replica 7.8.
Measured after (ice-a, invariant TSC, r3, uprobes on every `rdtsc` site + libc `clock_gettime`, `lab/baremetal/clock-sum.sh`), reads/op before -> after: w4kq32 primary 20.8 -> 4.3, replicas 11.6/16.9 -> 2.9/3.8; w4k1 primary 97 -> 44.5, replicas 70/79 -> 25/28 (QD1: per-iteration reads of idle spins). Remaining at QD32: loop read, store `poll_inner` (~1.7/op), `wake::mono_ns` (~0.7/op, only on poke/wake). op-cpu-gate: instr/op -0.3 % (r, w). s1 learned slice vs before (IOPS, mean of 4 A + 4 B rounds, ABBA + BAAB): SPDK w -1.7 %, r -5.7 % (ranges overlap: r A 38.4-41.1k, B 34.1-40.8k); kernel-NVMe (ABBA) w +3.5 %, r +2.9 %. Slice cuts (`flashstore_core_N.slice_cuts`, drains stopped by the slice with work left): r4kq32 0.07 per op, r4k1 0.001: the slice does not bind on 4K reads. With the span stamp fix, SPDK reads vs before: r4kq32 +1.1 % (BAAB), r4k1 +0.4 % (8 rounds ABBAABBA: 2524 vs 2514 IOPS); kernel-NVMe sibling: r4kq32 +0.8 % (ABBA), r4k1 +3.7 % (8 rounds: 2296 vs 2214).
Left (not per op): store `poll_inner` reads its own `MonoClock` per poll (store time base differs from the loop's; one fastclock read per store poll), pipe resume / repop retry 100 us budgets (rare paths), lab-feature diag timers.

## Amendment 5 (2026-10-24): background work out of the drain slice; fair share with it
- Work no message caused is kept out of `Slice::learn`: listing continuations (adr 0522), store background work timed on the store's clock (`Shard::bg_ns`: run merges, compactions, checkpoint start / slices / completions, idle compaction and defrag; `PgStoreOps::bg_ns` adds PG deletion steps) and compaction helper steps (`Cl::helper_ns`).
- Fair share: a drain may take as long as the previous iteration's background work took (`Slice::share`, at least `SLICE_NS`). Under contention messages and maintenance get half of the core each; with no background work the slice is unchanged.
- Rationale: counted in, a 3-5 ms merge slice made the learned cost ~1 ms per unit and cut every drain to its first message; with correct learning a 100 us drain against back-to-back merge slices still gave messages ~3 % of the core. Both held cross-core messages in the inbox for the whole merge backlog. Measurements: doc/perf/omap-tail-stall-20261024.md.

## Amendment 6 (2026-10-29): inbox drain share per source core
- `XPort::pump` gives every source core its own share of a drain: one work slice (am. 4, fair share of am. 5), at least the work units this core's link-event pump handed on since the previous drain (`Slice::start_drain`, `Slice::add_link`); work only, no message count bound (a message counts at least one store block, `SLICE_MIN`, so the slice bounds runs of small messages; the former 64-message bound predates the work slice). A source's share ends after its message that fills it (the first message of every source runs); round-robin over the source rings is unchanged. One code path for every driver (knet `KCore`, `rt::Core`, PG-only cores).
- Rationale: the link-event pump runs once per received chunk, each run with a fresh slice, so the own links hand on all their input of an iteration; the inbox had one slice per iteration in total. On a saturated PG core (one hot omap object, the learned slice smaller than one op) ~5 own-link ops and 1 forwarded op ran per iteration, and forwarded clients waited ~15x longer than own-link clients. Measurements: doc/perf/omap-hot-object-20261029.md.
- Consequences: a drain is bounded by one share per source core instead of one slice in total: with idle own links and a backlog on every source, (cores - 1) slices (4 cores: 300 us). Forwarded and own-link clients of a PG core get the same service rate; message decode of a hot PG's clients stays on their connection cores. A hot PG core runs more ops per iteration, so fewer store polls per op: per-poll background quanta (run compaction steps, adr 0476) lag sooner under the same write rate; a compaction whose input left is dropped at once (adr 0476 am. 12), so a lag holds no memory beyond the live runs (A/B: doc/perf/omap-hot-object-20261029.md).
- Alternatives: one slice per iteration for the own links too (cuts own-link batches: more iterations and per-iteration overhead per op); own-link ops through a local inbox (every driver changes); one total inbox budget matched to the own-link work (sources with uneven load stay unfair); slice / sources per source (a lone source, e.g. a single client stream, gets a fraction of today's slice).
